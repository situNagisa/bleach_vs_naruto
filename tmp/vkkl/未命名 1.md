vkkl 对象关系梳理

你的 vkkl 设计其实很清楚：薄 RAII 句柄 + 析构时 vkDestroy*，并不负责“父子所有权图”。  
不优雅的感觉，多半来自：Vulkan 对象天然是依赖图，而 C++ 成员析构顺序/谁存 device 句柄要你自己保证。

下面按“谁创建、谁销毁、必须比谁活得久”来理。

───

1. 你现在的封装在干什么

每个类型基本是同一种模式：

xxx_observer  = 原始句柄 + 销毁/使用时需要的父句柄（device / instance / pool…）
xxx           = observer + 析构时 destroy/free（独占所有权）

例如：
```shell
┌──────────────────────┬─────────────────────────────────┬──────────────────────────────────────────────┐
│ 类型                 │ 析构调用                        │ 析构时需要还活着的“父”                       │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ instance             │ vkDestroyInstance               │ （顶层）                                     │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ device               │ vkDestroyDevice                 │ （逻辑上 instance 还在，但 destroy device    │
│                      │                                 │ 不传 instance）                              │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ surface              │ vkDestroySurfaceKHR(instance,   │ instance                                     │
│                      │ …)                              │                                              │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ swapchain            │ vkDestroySwapchainKHR(device,   │ device                                       │
│                      │ …)                              │                                              │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ buffer / image /     │ vkDestroy*(device, …)           │ device                                       │
│ fence / …            │                                 │                                              │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ command_buffer       │ vkFreeCommandBuffers(device,    │ device + command_pool                        │
│                      │ pool, …)                        │                                              │
├──────────────────────┼─────────────────────────────────┼──────────────────────────────────────────────┤
│ descriptor_set       │ vkFreeDescriptorSets(device,    │ device + descriptor_pool                     │
│                      │ pool, …)                        │                                              │
└──────────────────────┴─────────────────────────────────┴──────────────────────────────────────────────┘
```


所以：RAII 只保证“有人析构时会 free”；  
“父对象比子对象活得久”要靠声明顺序 / 显式清空顺序 / 别在父死后还拿着子。

这不是你封装错了，是 Vulkan 的模型就是这样。

2. Vulkan 对象依赖总图（按生命周期）

VkInstance
├── VkDebugUtilsMessengerEXT          (需要 instance)
├── VkPhysicalDevice                  (非拥有，不能 destroy)
├── VkSurfaceKHR                      (需要 instance；还依赖窗口/平台 surface)
│
└── VkDevice                          (从 physical device 创建)
    ├── VkQueue                       (非拥有，随 device 消失，不要 destroy)
    ├── VkSwapchainKHR                (需要 device + surface 仍有效)
    │   ├── VkImage[]                 (swapchain 拥有！不要 vkDestroyImage)
    │   └── 你创建的 VkImageView[]   (先于 swapchain 销毁)
    │
    ├── VkCommandPool
    │   └── VkCommandBuffer           (allocate/free 或 pool 一起毁)
    ├── VkDescriptorPool
    │   └── VkDescriptorSet           (free 或 pool 一起 reset/毁)
    │
    ├── VkDeviceMemory
    ├── VkBuffer  ──bind──► memory
    ├── VkImage   ──bind──► memory
    │   └── VkImageView               (先于 image 销毁；image 先于 memory)
    ├── VkBufferView                  (先于 buffer)
    ├── VkSampler
    ├── VkShaderModule
    ├── VkDescriptorSetLayout
    ├── VkPipelineLayout              (依赖 set layouts 在创建时存在)
    ├── VkRenderPass
    ├── VkPipeline / PipelineCache
    ├── VkFramebuffer                 (依赖 image views / render pass)
    ├── VkFence / VkSemaphore / VkEvent
    └── VkQueryPool

读图规则：

• 箭头上方/外侧更“老”、活得更久
• 销毁顺序 ≈ 创建顺序的反序
• VkQueue / VkPhysicalDevice / swapchain 内部 VkImage：你不拥有，别当 RAII 去 destroy

3. 按“父句柄存在哪里”分类（对照你的 vkkl）

A. 顶层：Instance 族

┌─────────────────────────────┬───────────────────┬──────────────────────────────────────────┐
│ 对象                        │ 父                │ 备注                                     │
├─────────────────────────────┼───────────────────┼──────────────────────────────────────────┤
│ vkkl::instance              │ 无                │ 最后毁                                   │
├─────────────────────────────┼───────────────────┼──────────────────────────────────────────┤
│ vkkl::debug_utils_messenger │ instance          │ 先于 instance 毁                         │
├─────────────────────────────┼───────────────────┼──────────────────────────────────────────┤
│ vkkl::surface               │ instance          │ 先于 instance；swapchain 先于 surface 毁 │
├─────────────────────────────┼───────────────────┼──────────────────────────────────────────┤
│ VkPhysicalDevice            │ instance 枚举出来 │ 只是句柄，不 destroy                     │
└─────────────────────────────┴───────────────────┴──────────────────────────────────────────┘

B. 设备：几乎所有东西的父

┌──────────────┬─────────────────┬─────────────────────────────────────────────────────────────────────┐
│ 对象         │ 父              │ 备注                                                                │
├──────────────┼─────────────────┼─────────────────────────────────────────────────────────────────────┤
│ vkkl::device │ 逻辑上 instance │ vkDestroyDevice 不传 instance，但 instance 应仍有效直到 device 没了 │
├──────────────┼─────────────────┼─────────────────────────────────────────────────────────────────────┤
│ VkQueue      │ device 取出来的 │ 不要封装成 destroy 型 RAII                                          │
└──────────────┴─────────────────┴─────────────────────────────────────────────────────────────────────┘

C. 典型 device 孩子（析构只记 device）

这些在你库里模式完全一样：{device, handle} → destroy

• swapchain, buffer, image, image_view, buffer_view
• device_memory, sampler, shader_module
• descriptor_set_layout, descriptor_pool, pipeline_layout
• pipeline, pipeline_cache, render_pass, framebuffer
• fence, semaphore, event, query_pool, command_pool

规则一句话：device 必须比它们都活得久。

D. “池子分配出来”的特殊孩子

┌────────────────┬──────────────────────────┬─────────────────────────────────────────┐
│ 对象           │ 父                       │ 析构                                    │
├────────────────┼──────────────────────────┼─────────────────────────────────────────┤
│ command_buffer │ device + command_pool    │ vkFreeCommandBuffers                    │
├────────────────┼──────────────────────────┼─────────────────────────────────────────┤
│ descriptor_set │ device + descriptor_pool │ vkFreeDescriptorSets（池要有 FREE_BIT） │
└────────────────┴──────────────────────────┴─────────────────────────────────────────┘

额外规则：

• 也可以 不 free 单个，直接 vkDestroyCommandPool / vkDestroyDescriptorPool 一把清  
• 若 pool 先毁，再 free set/cmd → 非法  
• 所以：要么 RAII free 单个且 cmd/set 成员声明在 pool 后面（后声明先生效析构），要么 pool 拥有一切、单个只做 observer

E. 绑定关系（不是 destroy 父子，但顺序要命）

image_view  ──依赖──► image  ──bind──► device_memory
buffer_view ──依赖──► buffer ──bind──► device_memory

正确销毁顺序：

1. image_view / buffer_view
2. image / buffer
3. device_memory

你 vulkan_image 现在是：

device_memory _memory;  // 声明最早 → 析构最晚  ✓
image         _image;
image_view    _view;    // 声明最晚 → 析构最早  ✓

这个成员顺序是对的。  
~vulkan_context 里手动 _view → _image → _memory 也是对的。

4. Swapchain 这条最容易踩坑

surface + device
    → swapchain
        → images[]          （swapchain 拥有，vector<VkImage> 裸句柄 ✓）
        → image_views[]     （你创建，vkkl::image_view ✓）
        → 每张图一个 render_finished semaphore（常见）

销毁顺序：

1. 等 GPU idle / fence 完成
2. image_views
3. 与 swapchain 绑定的 per-image sync（如 render_finished）
4. swapchain
5. （resize 时）再创建新 swapchain；旧 surface/device 仍在
6. 最后才 surface → device → instance

不要对 _swapchain_images[i] 做 vkDestroyImage。  
你现在用裸 VkImage 存，是正确选择。

5. 对照你 vulkan_context 的拥有关系

成员声明（创建偏早 → 声明靠前）：

_instance
_debug_messenger
_surface
_physical_device          (非拥有)
_device
_graphics_queue/_present  (非拥有)
_swapchain
_swapchain_images         (非拥有，跟 swapchain)
_swapchain_image_views
_render_finished
_slots[]                  (pool/sem/fence/depth_image)

析构里你 显式 按反序清，这是对的，因为：

1. 要先 vkDeviceWaitIdle
2. C++ 默认成员析构顺序是 声明的反序，但中间还有 bootstrap、atomic 等，显式清更安全、可读
3. primary_command_buffer 是裸 VkCommandBuffer：  
   销毁 pool 时会一起释放；若改成 vkkl::command_buffer，必须保证 先 free buffer 再 destroy pool

这是“创建期依赖”≠“全程持有依赖”，和 fence/image view 不同。

7. 为什么你会觉得“不优雅”

因为现在有 三层不同性质的关系 被同一个 RAII 外观盖住了：

┌────────────┬───────────────────────────────────────────┬────────────────────────────────┐
│ 关系类型   │ 例子                                      │ RAII 能不能单独表达            │
├────────────┼───────────────────────────────────────────┼────────────────────────────────┤
│ 销毁父句柄 │ 几乎所有东西需要 device                   │ 存 VkDevice 值即可（你在做的） │
├────────────┼───────────────────────────────────────────┼────────────────────────────────┤
│ 分配父池   │ cmd ← pool，set ← pool                    │ 必须双句柄 / 或 pool 独占      │
├────────────┼───────────────────────────────────────────┼────────────────────────────────┤
│ 绑定/借用  │ image↔memory，view→image，swapchain image │ 顺序约束，不是 shared_ptr 父子 │
├────────────┼───────────────────────────────────────────┼────────────────────────────────┤
│ 非拥有句柄 │ queue、physical device、swapchain image   │ 不该有 destroy 析构            │
└────────────┴───────────────────────────────────────────┴────────────────────────────────┘

vkkl 目前只优雅地覆盖了第 1 类 + 部分第 2 类。  
第 3、4 类只能靠 上层组合类型（如你的 vulkan_image、vulkan_context）保证顺序——这是正常分层，不该全塞进 vkkl::image。

8. 实操规则（比“优雅 API”更重要）

9. device 活得比几乎所有 vkkl::* 长  
10. instance 活得比 surface / device 长  
11. view → image/buffer → memory  
12. swapchain views / per-image semaphores → swapchain → surface  
13. 单个 command_buffer / descriptor_set 先于其 pool（若各自 free）  
14. 任何 destroy 前：GPU 不再用它（idle 或 fence/timeline epoch）  
15. 裸句柄 = 我不拥有；有 vkkl::xxx = 我拥有  

你 ~vulkan_context 里 vkDeviceWaitIdle 再逆序清空，就是在做第 6 + 反序销毁。

───

9. 和“优雅封装”的边界（方便你之后改）

若只整理关系、暂不重写 API，建议心智是：

vkkl::*          → 单对象 destroy/free 的唯一所有者（non-owning 用 observer / 裸句柄）
组合结构体       → 表达绑定与销毁顺序（vulkan_image, frame_slot, context）
workflow/同步    → 表达“何时允许 destroy”（fence/epoch），不属于 vkkl

不必强行：

• image 里 shared_ptr<device>（重、也解决不了 GPU in-flight）  
• swapchain 自动 destroy 内部 images（本来就不是你的）  
• 所有对象树状 parent*（Vulkan 是 DAG + 绑定，不是简单树）

10. 最小记忆版

Instance
  └─ Surface
  └─ Device
       ├─ Queue（不销毁）
       ├─ Swapchain →（内部 Images 不销毁）→ 你的 ImageViews
       ├─ Pool → Buffer/Set（allocate）
       ├─ Memory ← bind ← Image/Buffer ← View
       └─ Fence/Semaphore/Pipeline/...

销毁：叶子 → 根；使用中的对象先等 GPU。
