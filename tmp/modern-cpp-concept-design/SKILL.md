# 现代 C++ Concept 编码规范

所有 C++ concept编码任务都适用本 skill。

## 设计原则

按“原语 → concept → 派生算法”组织接口：先提供操作和关联类型，再用 concept 组合约束，最后基于 concept 和原语实现算法、派生类型特征及更强的 concept。

- **原语**表达最基本的行为或关联类型。函数调用可以是普通函数，也可以是允许用户定制的 CPO；关联类型可以直接取得，也可以通过允许用户特化的 trait 提供。
- **Concept**定义这些原语需要满足的契约，包括可用性、结果类型、类型之间的关系，以及确有必要的异常保证。
- **派生算法**消费契约，通过原语完成操作；不重复实现原语的查找、分派或类型提取逻辑。

原语不承担完整 concept 的语义约束，但可以包含使检测和调用成立的最低限度约束，例如排除无可用实现的 CPO 分支、检测关联类型是否存在。不要让原语反过来依赖由它组成的 concept，以免产生约束递归。

遵循用户要求、仓库约定和实际工具链支持的语言标准。此 skill 规定 concept 的设计与组织方式，命名、格式等通用编码规则沿用项目规范。

## 按需读取参考

- 设计或修改 concept 时，读取 [concept 编写方法](references/concept.md)，确定原语、组合约束和派生算法之间的依赖。
- 操作需要用户定制，或需要修改调用分派时，读取 [CPO 编写方法](<references/CPO(custom point object).md>)。
- 关联类型需要用户定制，或需要修改 trait 默认行为时，读取 [类型特征编写方法](references/类型特征.md)。

参考中的代码用于说明设计骨架。落地时补全声明、限定名、分支和依赖，修正示意代码的拼写或语法问题，并按当前语言标准编译验证；不要将骨架直接视作可编译实现。

## 确定概念契约

从算法实际使用的操作和类型关系出发，列出必要原语，再确定哪些原语需要成为自定义点。已有普通函数、标准库设施或关联类型足够时，直接使用；不要为每个原语强制增加 CPO 或可特化 trait。

对每个原语明确以下内容：

- 接收对象和参数的 cv/ref 限定，是否支持常量、左值或右值调用。
- 返回值或关联类型的要求：精确类型、可转换类型，或满足另一个 concept。
- 是否要求 `noexcept`，以及有效期、相等性保持、复杂度等无法由约束表达式证明的语义要求。
- 若允许定制，允许的入口、默认行为，以及多个入口同时存在时的优先级。

优先复用语义吻合的标准库或项目 concept。不要为了实现方便额外要求可复制、默认构造或相等比较等算法并不需要的能力；也不要用一次表达式检测冒充具有额外语义要求的标准 concept。

## 实现原语

### 函数调用与 CPO

需要 CPO 时，采用参考中的具名实现命名空间、策略枚举、`choice_result`、编译期选择器、调用对象类型和 `inline constexpr` 对象的组织方式。

- 用 `requires` 和 `if constexpr` 检测可用策略，在有效分支内计算异常规格。成员调用、ADL、前缀函数及默认实现均按具体契约选择；明确优先级，不机械加入所有分支。
- 让 `operator()` 的参与约束、条件 `noexcept` 和函数体分派共享选择结果。无可用策略且无默认实现时，调用应在约束检查时被排除。
- 检测、异常规格和实际调用使用相同的表达式、参数顺序与值类别。按契约完美转发，并用 `decltype(auto)` 保留需要保留的返回引用。
- 选择器只检查类型和表达式，不执行用户操作。优先使用无参的 `choice<Args...>()` 进行类型驱动的选择；若选择器接收参数，确认普通运行时调用不会因 `consteval` 而要求实参值是常量表达式。
- ADL 分支按参考设置普通查找屏障，并通过实现命名空间中的辅助函数检测和调用，避免找到 CPO 对象自身或发生递归。算法调用公开 CPO 时使用明确的命名空间限定。

原语只决定操作如何发生；“返回类型是否满足业务 concept”等组合约束放在 concept 层。

### 关联类型与 trait

需要用户定制的关联类型时，用类模板提供特化入口，用别名模板公开提取结果。别名模板本身不能作为特化入口。

- 有默认行为时，从约定的嵌套类型或其他原语推导；没有默认行为时，保留可特化且不提供 `type` 的主模板。
- 缺失嵌套类型应使对应检测不满足，而不是触发主模板实例化的硬错误。可以使用有效的空主模板和受约束的偏特化，仅在嵌套类型存在时提供默认 `type`。
- 在 `_t` 别名处检查 `typename xxx_yyy<T>::type` 是否存在，但不要认为此检查能捕获主模板定义内部的一切实例化错误。
- 按契约决定是否使用 `::std::remove_reference_t` 或 `::std::remove_cvref_t`。明确用户应为哪个类型特化，并让特化查找与默认行为采用一致的类型归一化规则；不要无条件丢弃 cv/ref 信息。

## 组合约束

Concept 直接组合原语及已有 concept，避免复制 CPO 的成员、ADL 等检测分支。否则 concept 与实际调用可能选择不同实现。

- 只检测表达式是否合法时使用简单要求；检测关联类型时使用类型要求；检测结果类型或不抛异常保证时使用复合要求；要求布尔条件成立时使用嵌套要求。
- `requires { predicate<T>; }` 只检查表达式是否有效，不检查它的真假。需要条件成立时使用 `requires { requires predicate<T>; }`，或直接以 `&& predicate<T>` 组合。
- `requires(T&& value)` 中具名的 `value` 仍是左值。检测左值操作时直接使用它；检测转发调用时使用 `::std::forward<T>(value)`。检测必须与算法实际使用的 cv/ref 和值类别一致。
- 在需要某个关联类型或表达式的进一步约束前，先检查其存在性；利用 `&&` 的约束短路组织依赖。对于预期不满足条件的类型，应得到 `false`，避免辅助模板实例化中的硬错误。
- 更强的 concept 显式复用基础 concept，例如 `refined<T> = base<T> && ...`。不要展开重写基础约束来期待重载自动识别其关系：约束包含关系取决于原子约束的身份和参数映射，并非一般的逻辑等价推理。

将无法由编译器验证的语义要求写进契约。区分“约束表达式求值为真”和“类型完整满足概念语义”，不要宣称 `requires` 已经证明运行时行为、生命周期或复杂度。

## 派生算法与验证

算法使用能覆盖自身需求的最弱 concept，并通过公开原语完成操作。派生类型特征依赖基础 concept 和原语；更强的 concept 组合基础 concept 与额外要求，保持依赖单向。

修改实现后，按本次改动选择有区分力的编译验证：

- 用满足条件的类型和接近但不满足的类型验证 `static_assert(concept_name<T>)` 与 `static_assert(!concept_name<T>)`，特别检查缺失关联类型、错误返回类型及无可用调用的情况。
- 涉及转发或返回引用时，覆盖相关的 cv/ref 组合；涉及异常规格时，核对抛异常与不抛异常的分支。
- 涉及 CPO 时，验证实际支持的定制入口、多个入口共存时的优先级，以及普通运行时实参的实际调用。
- 涉及 concept 细化及重载时，编译真实调用，确认选中预期重载且没有歧义。

不要只验证 concept 值为真；对本次修改影响的算法或 CPO，至少实例化一次实际调用，以暴露约束检查未覆盖的函数体错误。记录所用语言标准和未能验证的限制。

完成设计或审查时，说明原语与自定义点、concept 所表达的契约、派生接口的依赖，以及实际验证结果。发现问题时指出其属于原语实现、约束表达还是语义契约，并给出对应位置的修正。
