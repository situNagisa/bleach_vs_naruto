我的判断是：`consumer_promise::unhandled_stopped()` 应该把当前 task 以 `stopped` 结束，并沿 continuation 向上传播；不应该 `terminate()`，也不应该把父协程当作正常完成直接恢复。

要先区分两个时刻：

- `stop_token.stop_requested()`：只是有人请求停止，task 仍然可以完成当前安全阶段。
- `unhandled_stopped()`：某个被 `co_await` 的 sender 已经以 `set_stopped` 完成。此时 `co_await` 没有结果，当前协程后面的代码不能继续执行。

正确流程应该是：

```text
子 sender: set_stopped
→ consumer_promise::unhandled_stopped()
→ 跳过当前 consumer 剩余代码
→ 向父 continuation 传播 stopped
→ 一直传播到 task-as-sender 的边界
→ set_stopped(receiver)
→ operation_state 销毁协程帧和局部资源
```

核心实现语义类似：

```cpp
auto unhandled_stopped() noexcept -> std::coroutine_handle<>
{
    return _continuation.unhandled_stopped();
}
```

注意这里不能是当前的裸 `std::coroutine_handle<>`。它只知道“正常恢复哪个协程”，不知道“如何向那个协程传播 stopped”。需要一个 stop-aware continuation：

```cpp
struct stoppable_continuation
{
    auto handle() const noexcept -> std::coroutine_handle<>;
    auto unhandled_stopped() const noexcept -> std::coroutine_handle<>;
};
```

`set_continuation(parent)` 保存：

- 父协程地址；
- 正常完成时恢复父协程的方法；
- stopped 时调用 `parent.promise().unhandled_stopped()` 的类型擦除回调。

这正是 stdexec 的参考做法：[__with_awaitable_senders.hpp](/D:/project/stdexec/include/stdexec/__detail/__with_awaitable_senders.hpp:55) 和 [__task.hpp](/D:/project/stdexec/include/stdexec/__detail/__task.hpp:526)。

但只改 `consumer_promise` 还不够，当前 nagisa 接口有两个阻碍：

1. [jump_to_continuation](/D:/project/nagisa/libs/concurrency/include/nagisa/concurrency/_coroutine/component/continuation.h:96) 保存的是裸 handle，传播 stopped 所需的父 promise 类型信息已经丢失。

2. [destroy_after_resumed](/D:/project/nagisa/libs/concurrency/include/nagisa/concurrency/_coroutine/component/exit.h:22) 只在正常 `await_resume()` 时销毁子协程。stopped 路径不会调用 `await_resume()`，所以 awaiter 必须增加 RAII 析构兜底，否则传播 stopped 后会泄漏协程帧。

因此我建议在 nagisa 中把它拆成三组独立能力：

```text
with_stop_token
    只负责保存、查询、透传 stop_token

propagate_stopped_to_continuation
    负责 unhandled_stopped 的向上传播

terminate_on_unhandled_stopped
    给明确不允许 stopped 的协程使用
```

现在 [with_stop_token](/D:/project/nagisa/libs/concurrency/include/nagisa/concurrency/_coroutine/component/stop_token.h:219) 继承 `without_stop_token`，把“能收到取消请求”和“收到 stopped 后 terminate”绑在一起了，我认为这个组合不合理。

对于你这个渲染架构，还需要规定安全取消点：

- 尚未取得 slot：可以取消，但 `frame_slots` 必须把挂起 waiter 从队列注销。
- 已经取得 slot：slot 必须用 RAII 保证归还，不能只依靠最后的 `slot.release()`。
- 已经 `begin_frame`/取得 swapchain image：最简单可靠的策略是暂时屏蔽取消，完成 submit、GPU wait、entity join、slot release 后，再向外报告 stopped。
- `frame_context` 销毁前，所有引用它的 entity 必须完成或被停止并 join；不能让 stopped unwind 直接销毁 `run_frame`，而 entity 仍持有 `fc&`。

所以最终结论是：

> `unhandled_stopped()` 只负责“终止当前协程控制流并传播 stopped”，不负责 Vulkan、slot、barrier 等业务清理。业务清理由 RAII 和结构化子任务清理保证。以当前接口，不能只在 `consumer_promise` 里硬写一行解决，需要先补 stop-aware continuation 和取消路径的 awaiter 所有权。
