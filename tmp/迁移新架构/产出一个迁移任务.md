## 一、仓库当前描述的架构

注意：这是“当前文件写着什么”，不代表所有细节仍获用户认可。尤其 retirement sender/free-list generation 是此前 agent 过度写入的内容。

   - 在 `main_scope` 和 main scheduler 上启动各个 `entity.main(context)`。
   - 主循环采集事件，然后每帧调用 `render_workflow.submit()`。

2. `source/client/context.h`
   - 持有 `vulkan_context`、`render_workflow`、`render_scope`。
   - 另有 main scheduler、main scope 和 main thread。
   - shutdown 当前分别排空 render scope/main scope，并处理 workflow generation。

   - 规定 `entity.main` 与 render task 是两个长期任务。
   - `entity.main` 调用 `graphics::render(...)`，把返回 sender 启动到 `render_scope`。

4. `docs/render/renderable.md` 与 `include/bvn/graphics/renderable.h`
   - 定义 `graphics::render` CPO 和 `renderable` concept。
   - 当前 `render(...)` 返回长期 sender/协程，不是单帧函数。
   - renderable 与长期 render task 直接绑定。

5. `docs/render/render-task.md`
   - 当前规定长期 render task 自己初始化 pipeline/buffer/secondary pool。

## 二、用户提出的新架构

核心变化：不再存在独立的长期 render task。一个 `entity.main(context)` 同时参与逻辑阶段和渲染阶段。

每轮大致为：

```cpp
task entity::main(context& context)
{
    auto pool = ...;

    while (!stop)
    {
        auto input = co_await on_frame();

        auto snapshot = should_compute()
            ? compute(input)
            : interpolate(input);

        auto frame_slot = co_await prepare_frame_render();

        render(frame_slot, snapshot);
    }

    co_await scope.on_empty();
}
```

workflow 每帧提供两个 rendezvous：

```cpp
auto workflow::frame() -> void
{
    auto input = collect_input();

    // 第一阶段：放行 entity.main 做 compute/interpolate
    sync_wait(logic_waiters);

    // 保守但正确的 GPU 准备
    auto frame_slot = create_frame_slot();
    begin_frame(frame_slot);

    // 第二阶段：把 frame_slot 交给 entity.main 做 render
    sync_wait(render_waiters);

    end_frame(frame_slot);

    // 保守等待 GPU 完成后才结束资源生命周期
    sync_wait(when_all(frame_slot.fence, swapchain));
    ~cmd;
    ~pool;
}
```

这里的 `render(frame_slot, snapshot)` 只是占位符：
- 与当前 `graphics::render` CPO 无关；
- 与当前长期 render task 无关；
- 随便用户怎么写，是用户自定义的代码。用户可以产出任意数量个`secondary command buffer`用于绘制

## 三、必须遵守的设计边界

- `~cmd`、`~pool` 和每帧等待 fence/swapchain 是刻意选择的保守正确基线。
- 允许性能较低；先保证资源生命周期显然正确。
- 不得自行替换成 retirement sender、free list、跨 generation ownership transfer 或 frames-in-flight 优化。
- 上述优化以后可以讨论，但现在不能写入正式架构或规范。
- `~cmd/~pool` 当前主要表达生命周期边界，不要擅自推断最终 C++ owner/API。
- main/render 合并的是长期任务结构；不要把占位的 `render()`重新解释为旧 render task。
- 保留全局决策 `simulator -> render 使用双缓冲 snapshot + interpolate`，除非先指出它与新伪代码的冲突并请求用户裁决。
