## 一、新架构复述（区分已确认 / 未确认）

### 1.1 已确认的部分

1. **不再有独立的长期 render task。** 一个 `entity.main(context)` 是唯一的长期协程，**同时**承担逻辑阶段和渲染阶段。旧的「entity.main 只负责 spawn 一个 `graphics::render(...)` 长期协程到 render_scope」这套结构被删除。
2. **每帧两个 rendezvous**，由 workflow 提供：
   - 阶段一（逻辑）：放行 entity.main 做 `compute` / `interpolate`；
   - 阶段二（渲染）：把 `frame_slot` 交给 entity.main，让它把内容画进去。
3. **workflow 每帧的编排顺序**（保守正确基线）：采集输入 → 放行逻辑 waiters → 创建并 begin `frame_slot` → 放行渲染 waiters → end `frame_slot` → 等待 `fence` + swapchain → 析构该帧的 `cmd`/`pool`。
4. **保守正确基线是刻意选择**：单帧槽、完全串行、每帧建/销资源、每帧等 fence+swapchain。**明确禁止**现在写入：retirement sender、free list、跨 generation 所有权转移、frames-in-flight 优化。允许性能低，先保证生命周期显然正确。
5. **`render(frame_slot, snapshot)` 是占位符**：与旧 `graphics::render` CPO 无关、与旧 render task 无关，是用户自定义代码，可产出**任意数量**的 secondary command buffer。
6. **游戏主体只认识 entity.main** 这一个接口（这条哲学从旧 boot.md 保留）。
7. **全局决策「simulator → render 用双缓冲 snapshot + interpolate」保留**（除非我先指出它与新伪代码的冲突并请你裁决——见下方 Q5）。

### 1.2 未确认 / 占位——不得写成正式契约

- **所有名字都是占位**：`on_frame` / `prepare_frame_render` / `frame()` / `create_frame_slot` / `begin_frame` / `end_frame` / `logic_waiters` / `render_waiters` / `should_compute` / `compute` / `interpolate` / `scope.on_empty`。
- **`~cmd` / `~pool` 只表达「生命周期边界」**，不代表最终 C++ owner 或 API 形状。
- **两个 rendezvous 的落地机制**（是不是就是两个 `co_await`、跑在哪条 scheduler 上）未定。
- **entity 自有 secondary pool 的生命周期**：伪代码把 `auto pool = ...` 放在 `while` **之外**（每 entity 一份、长期存活），但 workflow 里每帧 `~pool`——这两处「pool」大概率不是同一个东西（见 Q2），需澄清。
- **合并的是「长期任务结构」**（main+render 合成一个协程），占位的 `render()` 不得被重新解释成旧 render task。
- **renderer concept 二分是否保留**、**跨 entity 绘制顺序是否定义**、**snapshot 是否仍跨线程零锁**，均未定。

### 1.3 一句话对照（仅供理解，最终文档只描述新架构）

| 维度        | 旧（当前文档/代码）                                    | 新（你的提案）                                    |
| --------- | --------------------------------------------- | ------------------------------------------ |
| 长期任务      | entity.main（逻辑）+ 独立 render task（渲染），两个协程      | 单个 entity.main，逻辑+渲染两阶段                    |
| 每帧驱动      | `render_workflow.submit()` 一次 rendezvous      | `workflow.frame()` 两次 rendezvous           |
| 内容入口      | `graphics::render` CPO + `renderable` concept | entity.main 内用户自写 `render()`，无 CPO/concept |
| 命令回收      | generation + retirement sender + free list    | 每帧建销、等 fence，无回收机制                         |
| in-flight | frames_in_flight=2、槽轮转                        | 单槽、完全串行                                    |

## 三、必须先与你确认的问题（不自行补全）

1. **Scheduler / scope 拓扑**：新架构里 main scheduler 与 render scheduler 是否还并存？entity.main 在哪条 scheduler 上跑、由谁驱动它的两个 rendezvous？`main_scope` / `render_scope` 二分是否合并成一个？（决定 boot.md / render-scheduler.md / context.h 的结构。）
2. **`~cmd`/`~pool` 到底指哪份资源，以及 entity secondary pool 的基线**：我的读法是——workflow 里 `~cmd`/`~pool` = **每帧新建的 frame_slot 自己的 primary command + pool**（等 fence 后析构）；entity 伪代码里 `while` 之外的 `pool` = **entity 自有 secondary pool，长期存活**。对吗？若对，保守基线下 entity 的 secondary buffer 每帧如何复用（每帧 reset 重录，因完全串行）？这条正是「保守基线」与被禁的 free-list 之间的边界，需要你明确裁定，我不擅自定。
3. **渲染阶段的合成与顺序**：多个 entity 产出的 secondary 是否仍由 workflow 用一个 primary `vkCmdExecuteCommands` 合成？跨 entity 的绘制顺序是**未定义**、还是按注册顺序 / 某确定序？（决定是否保留 model-ab / 顺序小节。）
4. **renderer concept 二分去留**：保守基线下是否仍需要 `global_env_renderer` / `frame_env_renderer` 两个 concept + 静态/动态转发这套，还是简化为一个 `frame_slot` 具体类型？（`renderable` concept + `render` CPO 我按「删除」处理，请确认。）
5. **sim/interpolate 与双缓冲的关系（潜在冲突，需裁决）**：伪代码 `should_compute() ? compute : interpolate` 把「推 sim」和「插值」折进同一个 per-frame 协程；而全局决策「双缓冲 + 插值」的立论是 **producer/consumer 跨线程零锁解耦**。若逻辑与渲染都在同一 entity.main 里顺序执行，双缓冲的「零锁跨线程」动机部分消解（但「上一帧+当前帧」两份快照做插值仍需要）。请裁决：**保留 sim 与 render 解耦的双缓冲**，还是**合并**？以及现有独立的 `preview_controller`（专做 sim/interp 的 entity）是折进 entity.main 还是继续独立？
6. **命名与文件结构**：`submit()`→`frame()` 是否定名？「render scheduler / `render_workflow`」这个名字在无 task 后是否改为「render workflow / frame workflow」？`render-task.md` / `renderable.md` 采「删除」而非「重命名」是否 OK？`render-scheduler/` 子文件夹在 model-ab 删除后是否精简？
7. **未确认机制在 doc-spec 四分类里的落点**：这些占位机制先只锁「已确认骨架」为**设计/规范**，把未定细节明确标成 **现状/计划（TODO）**，还是等你逐条敲定后再一次成文？（决定这轮写多少、写进 spec 还是 impl。）
