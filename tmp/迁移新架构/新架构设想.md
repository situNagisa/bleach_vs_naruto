这是理想的写法，但在第二次循环的时候，一定会析构第一次循环的cmd，此时cmd可能还正在被使用，就会出错。所以导致必须把cmd放在循环外：
```cpp

```
但是放在循环外就要考虑帧槽数的问题了，就必须维护一个cmd数组：
```cpp
auto pool = ...;
auto cmd = ::std::vector(create(pool), in_flight_count);
while (!stop.stop_requested()){...}
```
这样在in_flight_count变化时，render task也要进行相应的处理，于是我们需要一个机制来通知render task in_flight_count发生变化了，这个机制是什么要思考一下。

这样因为render task是长生命周期任务而导致的，如果render只在一帧中运行一次，就没有这个问题

这版更接近可落地：先保证所有 snapshot 生产完成，再 begin frame，随后并行录制，全部录完后 end frame。阶段边界很清楚。

但当前伪代码还有几个硬问题：

1. `begin_frame()` 被 main 和 entity 各调用了一次。它只能由协调者调用；entity 应等待 `frame_ready` 并取得 generation。
2. `co_await barrier2.arrive()` 会挂起 entity，但之后没有 resume，`sync_wait(barrier2.waiters)` 会死锁。
3. main 没有等待 spawn 出去的完整 render 工作，可能直接进入下一轮并销毁两个 barrier。
4. `resume(waiters)` 会在 serial render scheduler 上内联恢复。entity 应马上切到并行的 recording scheduler。
5. consumer 在 arrive 前抛异常时，计数永远无法归零。barrier 必须支持 error/stop，或用 RAII arrival ticket。
6. `render_all_done` 实际只是“secondary 录制完成”，不是 GPU 执行完成，建议命名为 `record_all_done`。

我建议每帧创建一个不可重置的 `frame_round`：

```cpp
struct frame_round
{
	async_latch compute_done{consumer_count};
	async_broadcast<render_frame_generation> frame_ready;
	async_latch record_done{frame_consumer_count};
};
```

entity：

```cpp
auto entity::consumer(frame_round& round, input_type input) -> task
{
	auto snapshot = compute(input);

	round.compute_done.arrive();

	auto generation = co_await round.frame_ready.wait();

	co_await ::stdexec::schedule(recording_scheduler);

	// pool 仍归 entity 所有。
	auto frame = generation.bind(_secondary_command_pool);
	auto command = frame.allocate();

	render(snapshot, command.get());

	::stdexec::spawn(
		frame.retire(::std::move(command)),
		_retirements.get_token());

	round.record_done.arrive();
}
```

帧协调者：

```cpp
auto run_frame(input_type input) -> task
{
	auto round = frame_round{entity_count, frame_consumer_count};
	auto scope = ::exec::async_scope{};

	scope.spawn(entity1.consumer(round, input));
	scope.spawn(entity2.consumer(round, input));

	co_await round.compute_done.wait();

	co_await ::stdexec::schedule(render_workflow.get_scheduler());
	auto generation = render_workflow.begin_frame();

	round.frame_ready.set(generation);

	co_await round.record_done.wait();

	// 最后一个 recorder 可能在 recording scheduler 上触发 latch，
	// 所以 end 前必须显式回到串行 submit scheduler。
	co_await ::stdexec::schedule(render_workflow.get_scheduler());
	render_workflow.end_frame(generation);

	co_await scope.on_empty();
}
```

main 只等待完整的一帧：

```cpp
while (!stop)
{
	auto input = collect_input();
	::stdexec::sync_wait(run_frame(input));
}
```

这里实际上有三种同步语义：

- `compute_done`：只计数，不保存 waiter coroutine。
- `frame_ready`：一次性广播，并携带 generation。
- `record_done`：只计数，通知可以安全 end frame。

如果 consumer 是每帧新建的，就不需要第二组 waiter，也不需要在 `end_frame()` 后重新 resume entity。只有 consumer 是跨帧长驻协程时，才需要第四个 `frame_complete` 广播来放行下一轮。

另外我仍建议返回 `render_frame_generation`，不要返回裸 `frame_slot`。槽号、fence 与 generation 对应关系继续完全封装在 workflow 内。
