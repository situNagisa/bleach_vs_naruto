是的，scheduler 这一侧确实有 “parallel” 相关的东西，但**不是一个 `parallel=true` 的布尔属性**。  
stdexec / P2300 里至少有 **三套容易混在一起的 “parallel” 系列**：

1. 系统级 `parallel_scheduler`
2. scheduler 的 progress 保证 `forward_progress_guarantee`
3. bulk 算法的执行策略 `seq / par / par_unseq / unseq`

它们名字都像，职责完全不同。

---

## 一句话结论

| 名字 | 是不是 scheduler 属性 | 回答什么问题 |
|---|---|---|
| `get_parallel_scheduler()` / `parallel_scheduler` | 一种具体 scheduler | 系统并行执行上下文在哪里 |
| `get_forward_progress_guarantee` | 是，query 属性 | 这个 scheduler 的前向进度保证多强 |
| `bulk(par, n, f)` 的 `par` | 不是 scheduler 属性 | 这次 bulk 想怎么并行/串行执行 |

所以：  
**scheduler 有 “parallel 相关属性”，但不是一个叫 parallel 的 bool；而是 `forward_progress_guarantee`，外加一个叫 `parallel_scheduler` 的具体类型。**

## 1. `parallel_scheduler`：系统并行调度器

源码在 [`__parallel_scheduler.hpp`](D:\project\stdexec\include\stdexec\__detail\__parallel_scheduler.hpp)。

```cpp
auto get_parallel_scheduler() -> parallel_scheduler;

class parallel_scheduler {
  auto query(get_forward_progress_guarantee_t) const noexcept
    -> forward_progress_guarantee;   // 返回 parallel

  auto query(get_domain_t) const noexcept
    -> __parallel_scheduler_domain;  // 发布自己的 domain

  auto schedule() const noexcept -> __parallel_sender;
};
```

### 它是什么
- 进程/系统级的并行执行上下文入口
- 旧名是 `get_system_scheduler()`，已 deprecated，改名为 `get_parallel_scheduler()`
- 背后有可替换 backend：`parallel_scheduler_backend`
- 默认 backend 可能是 Windows thread pool / libdispatch / `static_thread_pool` 等

### 它解决什么
给你一个“系统默认并行后端”：

```cpp
auto sch = get_parallel_scheduler();
auto snd = schedule(sch) | then(...);
```

更重要的是：它对 `bulk_chunked` / `bulk_unchunked` 做 domain 定制。  
也就是说，它不只是“能 schedule 工作”，还提供了 bulk 的高性能落地路径。

### 和 domain 的关系
`parallel_scheduler` 会回答：

```cpp
query(get_domain) -> __parallel_scheduler_domain
```

而 `__parallel_scheduler_domain` 会在 connect 前把：

```text
bulk_chunked / bulk_unchunked
```

重写成：

```text
__parallel_bulk_sender
```

这正好接上你上一条关于 domain 的问题：  
**parallel scheduler 通过 domain 改写 bulk 的实现。**

---

## 2. `forward_progress_guarantee`：真正的 scheduler “parallel 属性”

这才是 scheduler 上的“属性系列”。

定义在 execution 前向声明里：

```cpp
enum class forward_progress_guarantee {
  concurrent,
  parallel,
  weakly_parallel
};
```

query 是：

```cpp
get_forward_progress_guarantee
```

源码里默认值是：

```cpp
// __schedulers.hpp
struct get_forward_progress_guarantee_t
  : __query<get_forward_progress_guarantee_t,
            forward_progress_guarantee::weakly_parallel, ...>
```

### 它是什么
这是 scheduler 对“执行代理前向进度”的承诺：

| 值 | 直观含义 |
|---|---|
| `concurrent` | 最强：可并发推进，适合阻塞调用场景更稳 |
| `parallel` | 中等：可以并行推进，但不保证 concurrent 那么强 |
| `weakly_parallel` | 最弱/默认：可能只有弱并行保证 |

### 怎么查

```cpp
auto g = get_forward_progress_guarantee(sch);
// 或
auto g = get_env(sch).query(get_forward_progress_guarantee);
```

对 `parallel_scheduler`：

```cpp
// __parallel_scheduler.hpp
return forward_progress_guarantee::parallel;
```

对某些 `run_loop` 相关 scheduler 也会返回 `parallel`。  
如果一个 scheduler 不声明，默认就是 `weakly_parallel`。

### 它不是什么
- 不是“这个 scheduler 能不能跑 bulk”
- 不是 bulk 的 `par` 政策
- 不是“这个算法会不会自动并行”

它只是：  
**这个执行上下文对任务推进能力给了什么保证。**

---

## 3. bulk 的 `par / seq / par_unseq / unseq`：执行策略，不是 scheduler 属性

这套来自 C++ 并行算法风格：

```cpp
sequenced_policy            seq
parallel_policy             par
parallel_unsequenced_policy par_unseq
unsequenced_policy          unseq
```

用于：

```cpp
bulk(par, n, f)
bulk_chunked(par, n, f)
bulk_unchunked(par, n, f)
```

### 它是什么
这是**某次 bulk 调用**的执行意图：

| policy | 意思 |
|---|---|
| `seq` | 按序，串行语义 |
| `par` | 允许并行，元素间有同步语义约束 |
| `par_unseq` | 允许并行 + 向量化/乱序更激进 |
| `unseq` | 单线程内可向量化/乱序 |

### 在 parallel scheduler domain 里怎么用
`__parallel_scheduler_domain` 重写 bulk 时：

```cpp
constexpr bool __parallelize =
  same_as<policy, parallel_policy>
  || same_as<policy, parallel_unsequenced_policy>;
```

然后：

- `par` / `par_unseq` → `__parallelize = true`，真正并行拆分
- 其他 policy → 走“顺序/非并行化”路径，但仍可走 parallel backend 的 bulk 入口

所以这里的 `par` 是：

**算法调用参数**，不是 scheduler 自己身上的属性。

## 4. 三者怎么一起工作

把它们串起来看最清楚：

```text
get_parallel_scheduler()
        |
        | query(get_forward_progress_guarantee)
        v
   guarantee = parallel     // 这个上下文的进度承诺

        |
        | query(get_domain)
        v
 __parallel_scheduler_domain
        |
        | transform_sender(bulk_chunked/bulk_unchunked)
        v
  看 bulk 的 policy:
    par / par_unseq -> 并行落地
    seq / unseq     -> 不并行化（或弱化）落地
```

示例：

```cpp
auto sch = get_parallel_scheduler();

// 1) scheduler 属性：进度保证
auto g = get_forward_progress_guarantee(sch);
// g == forward_progress_guarantee::parallel

// 2) 算法参数：这次 bulk 想并行
auto snd =
  just()
  | continues_on(sch)
  | bulk(par, 1000, [](int i) {
      // work
    });
```

这里发生了两层事情：

1. `sch` 说：“我是 parallel 进度保证，并且我有 `__parallel_scheduler_domain`”
2. `bulk(par, ...)` 说：“这次我想按 parallel policy 执行”
3. domain 把这个 bulk 改写成 parallel backend 的实现

## 5. 常见误解

### 误解 A：scheduler 有个 `parallel` bool
没有。  
真正属性是：

```cpp
get_forward_progress_guarantee -> enum
```

### 误解 B：`forward_progress_guarantee::parallel` 等于 bulk 的 `par`
不等。

- guarantee：这个 scheduler 的能力/承诺
- `par`：这次算法调用的执行策略

你可以有：

```cpp
// 进度保证是 parallel 的 scheduler
// 但 bulk 用 seq
bulk(seq, n, f)
```

也可以有：

```cpp
// 某个 scheduler 只保证 weakly_parallel
// 但你仍可写 bulk(par, ...)
// 只是后端可能不按你期望真正并行，或走默认实现
```

### 误解 C：只有 `parallel_scheduler` 才能并行
不对。  
任何 scheduler/domain 都可以定制 bulk。  
`parallel_scheduler` 只是标准里“系统并行上下文”的具体入口。

### 误解 D：domain 和 parallel 属性是一回事
也不对。

- `get_forward_progress_guarantee`：语义/能力声明
- `get_domain`：算法如何被改写/落地

`parallel_scheduler` 恰好两个都提供了：

```cpp
query(get_forward_progress_guarantee) -> parallel
query(get_domain) -> __parallel_scheduler_domain
```

## 6. 和 domain 的连接（接你上一条）

你上一条最困惑的是 domain。  
这里正好是最好的例子：

- **scheduler** 决定 work 在哪里跑：`parallel_scheduler`
- **domain** 决定算法如何被降低：`__parallel_scheduler_domain` 改写 bulk
- **policy** 决定这次 bulk 想要什么并行语义：`par/seq/...`
- **forward progress guarantee** 告诉库/用户这个上下文的进度承诺：`parallel`

所以“parallel 系列”不是一个属性，而是四层拼图里的不同层：

```text
where      = scheduler
how-lower  = domain
how-this-call = execution policy (par/seq)
promise    = forward_progress_guarantee
```

## 7. 最小记忆卡

1. **有没有 parallel 属性？**  
   有相关属性：`get_forward_progress_guarantee`，值可以是 `parallel`。

2. **有没有 parallel scheduler？**  
   有：`get_parallel_scheduler()`，旧名 `get_system_scheduler`。

3. **`par` 是什么？**  
   bulk 的执行策略，不是 scheduler 属性。

4. **它们怎么联动？**  
   `parallel_scheduler` 发布 domain，domain 看 bulk 的 policy 决定是否真正并行落地。
