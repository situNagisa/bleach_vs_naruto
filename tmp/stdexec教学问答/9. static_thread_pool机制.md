`exec::static_thread_pool` 本质上是“固定数量的 worker + 每个 worker 的本地队列 + 外部提交队列 + work stealing”。

```text
schedule(sender)
    ↓ connect
operation_state
    ↓ start()
判断提交者身份
    ├─ pool worker → 放进该 worker 的 local queue
    └─ 外部线程    → 放进目标 worker 的 remote queue，并唤醒它

worker 循环：
local pop → remote drain → steal others → sleep
```

### 1. 任务是什么

每个调度任务最终都是一个 `task_base`：

```cpp
struct task_base
{
    task_base* next;
    void (*execute_)(task_base*, uint32_t tid) noexcept;
};
```

`schedule()` 本身不执行工作。它返回 sender；`connect()` 产生 operation state；`start()` 才把 operation state 入队：

```text
schedule()
→ connect(receiver)
→ _opstate
→ start()
→ enqueue(this)
```

worker 取到任务后调用 `execute_()`，里面最终调用 receiver 的 `set_value()` 或 `set_stopped()`。对应实现在 [static_thread_pool.hpp](/D:/project/stdexec/include/exec/static_thread_pool.hpp:1195)。

所以对于 `continues_on`：

```text
前序 sender 完成
→ continues_on 保存完成结果
→ start(schedule(scheduler))
→ schedule operation 入队
→ worker 执行 schedule operation
→ set_value()
→ continues_on 转发此前保存的结果
→ coroutine 恢复
```

`continues_on` 不是直接切换线程，而是提交了一个很小的 schedule task。

### 2. worker 如何运行

每个 worker 都执行这个永久循环：

```cpp
while (true)
{
    auto [task, queue_index] = thread_state.pop();
    if (!task)
        return;
    task->execute_(task, queue_index);
}
```

见 [static_thread_pool.hpp](/D:/project/stdexec/include/exec/static_thread_pool.hpp:804)。

`pop()` 的查找顺序大致是：

1. 从自己的 local queue 尾部取任务。
2. 收集所有提交者发给自己的 remote queue。
3. 随机选择其他 worker，尝试从其 local queue 头部偷任务。
4. 没找到就短暂 yield。
5. 仍然没找到就进入条件变量休眠。

见 [try_pop](/D:/project/stdexec/include/exec/static_thread_pool.hpp:1010) 和 [pop](/D:/project/stdexec/include/exec/static_thread_pool.hpp:1116)。

### 3. local queue 和 remote queue 的区别

当 `start()` 在 pool 外部线程调用时：

```cpp
queue.queues_[thread_index].push_front(task);
thread_states_[thread_index]->notify();
```

它进入 remote queue，并唤醒目标 worker。

当 `start()` 本身就在某个 pool worker 上调用时：

```cpp
thread_states_[current_worker]->push_local(task);
return;
```

它进入当前 worker 自己的 local queue，不通知其他 worker。见 [enqueue](/D:/project/stdexec/include/exec/static_thread_pool.hpp:902)。

这是一个性能优化，基于这样的假设：

> 当前任务很快会返回 worker 调度循环，随后这个 worker 自己就会执行刚压入的任务。

即使 scheduler 最初是在另一个线程上取得的，只要真正调用 `start()` 时处于某个 pool worker，普通 scheduler 仍然会优先走当前 worker 的 local queue。

### 4. work stealing 不是“任何 local task 都能马上被偷”

local queue 是分块的 LIFO 队列，默认：

```cpp
numBlocks = 32;
blockSize = 8;
```

owner worker：

- 从尾部 `push_back()`。
- 从尾部 `pop_back()`。

其他 worker：

- 从头部 `steal_front()`。

关键是：当前正在写入的 block 暂时归 owner 独占。只有 owner 填满当前 block、前进到下一个 block，并调用 `grant()` 后，旧 block 才开放给其他 worker 偷取。

见 [steal()](/D:/project/stdexec/include/exec/detail/bwos_lifo_queue.hpp:521) 和 [grant()](/D:/project/stdexec/include/exec/detail/bwos_lifo_queue.hpp:629)。

因此它不是普通意义上“push 后所有 worker 立刻可见”的 deque，而是按 block 批量开放给 thief。

### 5. 套到你当前的程序

你的 poller 本身是 static thread pool 上的任务 A：

```text
worker A
→ 执行永久 poller 循环
→ run_once()
→ waiter.resume()
→ run_frame 在 A 上同步恢复
→ entity 的 continues_on 在 A 上 start()
```

于是两个 entity continuation 都被放进 A 的 local queue：

```text
A.local_queue.push(entity continuation 1)
A.local_queue.push(entity continuation 2)
```

但：

- A 永远待在 poller 的 `while` 中，不返回 `static_thread_pool::run()`。
- A 不会自己 `pop_back()`。
- 当前 block 只有两个任务，没达到默认的 8 个。
- block 没有 `grant()`。
- 其他 worker 的 `steal_front()` 看不到这两个任务。

所以它形成：

```text
worker A 正在永久执行 poller
A.local_queue 中有两个 continuation
其他 worker 无法偷
A 又永远不会返回执行自己的 local queue
```

这就是当前卡死的准确机制。它依赖的核心前提是：static thread pool 上的普通 task 应当最终返回调度循环；永久占用 worker，同时又在这个 worker 上提交后续任务，会破坏其 local-queue 快速路径的进展条件。
