你卡住的点很准：`domain` 不是“又一个调度器”，而是 **算法树在 connect 前如何被改写** 的机制。下面按“它是什么 → 为什么需要 → 怎么被找到 → 何时介入 → 和 scheduler 边界 → 真实例子”来拆。

---

## 1. 先给一句最硬的定义

> **Domain = 算法 lowering / rewrite 的策略标签。**  
> 它不执行任务，不拥有线程/stream，只在 `connect` 前回答：  
> “这个 sender 表达式，在当前上下文里，应该长成什么实现？”

所以：

- `scheduler` 回答 **where**：工作在哪个执行资源上跑
- `domain` 回答 **how**：同样的 `then/bulk/when_all`，落到哪套实现

---

## 2. 为什么一定要有 domain

用户想写统一管道：

```cpp
auto work =
    schedule(sched)
  | then(f)
  | bulk(par, n, g)
  | when_all(...);
```

但不同 backend 的“同一算法”实现完全不同：

| 算法 | CPU 默认实现 | GPU stream 实现 |
|---|---|---|
| `then` | 普通 receiver 包装 + 调函数 | 可能变成 stream callback / device 路径 |
| `bulk` | 循环或线程池并行 | 可能 launch kernel |
| `when_all` | 原子计数 + 取消联动 | stream 事件/设备侧汇合 |

如果没有 domain，你只能：

```cpp
gpu_then(...)
cpu_then(...)
gpu_bulk(...)
```

组合性会立刻崩。  
Domain 的目标就是：

> **用户仍写标准算法名；框架在启动前按上下文改写实现。**

这就是 `nvexec` 注释里那句：

> stream_domain is how the stream scheduler customizes the sender algorithms.

---

## 3. Domain 长什么样

最常见就是一个空 tag + `transform_sender`：

```cpp
struct my_domain {
  // OpTag 通常是 set_value_t 或 start_t
  template <class OpTag, class Sender, class Env>
  auto transform_sender(OpTag, Sender&& sndr, Env const& env) const {
    // 1) 不认识：原样返回
    // 2) 认识：返回“语义等价、实现不同”的另一个 sender
    return std::forward<Sender>(sndr);
  }

  // 可选：定制 consumers（sync_wait / start_detached 一类）
  template <class Tag, class Sender, class... Args>
  auto apply_sender(Tag, Sender&& sndr, Args&&... args) const {
    return Tag{}.apply_sender(std::forward<Sender>(sndr),
                              std::forward<Args>(args)...);
  }
};
```

默认是 `default_domain`：

1. 若 sender 的 tag 自己有 `transform_sender`，就调用它  
2. 否则原样返回

这很关键：**domain 定制分两层**

1. **算法 tag 自带的默认 lowering**  
   例：`bulk` 默认先变成 `bulk_chunked`
2. **执行上下文 domain 的后端定制**  
   例：GPU 的 `stream_domain` 把 `then_t` 换成 GPU `then_sender`

---

## 4. Domain 从哪里来：两条路径

框架不是“全局找一个 domain”，而是在 `connect` 时看两边：

### A. Completing domain（完成侧）

来源：sender attributes

```text
get_completion_domain<set_value_t>(get_env(sndr), env)
```

含义：

> “这个 sender 完成后，属于哪个 backend/world？”

常见来源：

- `schedule(gpu)` 的 attrs 声明 completion domain = `stream_domain`
- 某个 scheduler 的 attrs 通过 `get_completion_scheduler` 间接推出 domain

### B. Starting domain（启动侧）

来源：receiver environment

```text
get_domain(get_env(rcvr))
```

含义：

> “最终消费者/启动上下文希望按哪个 backend 启动？”

`get_domain` 的查找顺序大致是：

1. env 直接有 `get_domain` → 用它  
2. 否则若有 `get_start_scheduler` → 从该 scheduler 的 completion domain 推  
3. 否则 `default_domain`

---

## 5. 最关键：它在什么时候介入

看 `connect` 的真实路径：

```cpp
// connect 内部
auto new_sndr = transform_sender(sndr, get_env(rcvr));
// 然后再 new_sndr.connect(rcvr) / awaitable fallback ...
```

也就是：

```text
用户写的 sender 树
        |
        v
 transform_sender(sndr, env)   <--- domain 在这里工作
        |
        v
 真正 connect / start
```

`transform_sender` 是两阶段（代码注释写得很直白）：

```text
1) Completing-domain transform  (OpTag = set_value_t)
2) Starting-domain transform    (OpTag = start_t)
```

伪代码：

```cpp
auto sndr1 = completing_domain.transform_sender(set_value, sndr,  env);
auto sndr2 = starting_domain  .transform_sender(start,     sndr1, env);
connect(sndr2, rcvr);
```

并且它会递归：如果改写后类型变了，还可能继续按新 sender 的 completion domain 再 transform，直到稳定。

---

## 6. `transform_sender` vs `apply_sender`

这两个容易混：

| 机制 | 作用对象 | 时机 | 例子 |
|---|---|---|---|
| `transform_sender` | adaptor/factory 组成的 sender 树 | `connect` 前 | 把 `then` 改成 GPU then |
| `apply_sender` | consumer 算法本身 | 消费时 | 定制 `sync_wait` / `start_detached` |

可以记：

- `transform_sender`：改“管道零件”
- `apply_sender`：改“点火方式”

GPU 两边都用了：

- `transform_sender_for<then_t>`
- `apply_sender_for<sync_wait_t>`
- `apply_sender_for<start_detached_t>`

## 7. 用一个最小故事把整条链路跑通

```cpp
auto s =
    schedule(gpu_sched)
  | then(f)
  | continues_on(cpu_sched)
  | then(g);

sync_wait(std::move(s));
```

### 步骤 1：构造阶段（还没 domain 大显身手）

你只是在搭惰性树：

```text
then(
  continues_on(
    then(
      schedule(gpu),
      f),
    cpu),
  g)
```

此时大多还是“标准算法 sender”，不一定已经是 GPU 专用类型。

### 步骤 2：`sync_wait` 开始 connect

`sync_wait` 造 receiver，带 root env。  
`connect` 前调用：

```cpp
transform_sender(s, get_env(rcvr))
```

### 步骤 3：Completing domain 先动手

框架问：

```text
get_completion_domain(get_env(s), env)
```

因为前半段锚定在 `gpu_sched`，completion domain 往往是 `stream_domain`。  
于是 `stream_domain.transform_sender(set_value, ...)` 可能把：

```text
then(schedule(gpu), f)
```

改写成：

```text
nvexec::then_sender<..., f>
```

这就是 `nvexec` 里：

```cpp
transform_sender_for<STDEXEC::then_t>
```

做的事：若 child 是 stream-completing sender，就换成 GPU then 实现。

### 步骤 4：跨上下文后 domain 切换

`continues_on(cpu)` 之后，completion scheduler/domain 变成 CPU 侧。  
后半段 `then(g)` 不再被 GPU domain 接管，走默认 CPU 实现。

### 步骤 5：Starting domain 再过一遍

如果 receiver env 也带了某个 domain（或 start scheduler 能推出 domain），  
还会用 `start_t` 再做一次启动侧改写。

最后才真正：

```text
connect -> operation_state -> start
```

## 8. 默认 domain 其实也很有用：算法 lowering

不一定只有 GPU 才用 domain。  
标准算法自己也会借 `transform_sender` 做“规范化”。

`bulk` 就是例子：

```cpp
// bulk_t::transform_sender
// bulk(sndr, pol, n, f)  ->  bulk_chunked(sndr, pol, n, wrapped_f)
```

好处：

1. 只需要定制 `bulk_chunked`，`bulk` 自动吃到定制  
2. 用户 API 保持简单  
3. backend 只需实现更底层、更稳定的 primitive

所以 domain 体系不只是“插件后端”，也是 **算法分层编译**。

## 9. Domain 与 Scheduler 的边界（这是最易混的）

| | Scheduler | Domain |
|---|---|---|
| 本质 | 执行资源句柄 | 算法改写策略 |
| 关键问题 | 任务提交到哪 | 算法实现换成哪套 |
| 关键 API | `schedule` | `transform_sender` / `apply_sender` |
| 典型产物 | schedule-sender | 改写后的 sender 树 |
| 是否跑代码 | 间接负责执行 | 自己不跑业务代码 |
| 常见绑定 | scheduler attrs 发布 domain | domain 依赖 scheduler 上下文 |

### 正确关系

```text
scheduler
  ├── 提供执行资源（thread pool / CUDA stream）
  └── 发布 domain（“在我这里，算法请按我的手册 lowering”）
```

### 错误理解

- “domain 是更高级的 scheduler”  
  不是。
- “有了 domain 就不需要 scheduler”  
  不是。domain 不替代调度。
- “domain 在 runtime 每步动态切换线程”  
  不是。它主要在 connect/transform 期改写类型与实现。

一句话：

> **Scheduler 是车队；Domain 是这支车队的作业规范手册。**

---

## 10. 为什么有 completing / starting 两套 domain

因为“完成的世界”和“启动的世界”可能不同。

### Completing domain

关心：前驱完成后，后续 adaptor 该按谁的规则解释。  
适合：

- `then/let/bulk` 这类“接在某个上下文之后继续”的算法

### Starting domain

关心：最终从哪个世界点火。  
适合：

- consumer 路径
- 启动侧强制 backend 选择
- 某些 late customization

举个直觉例子：

```text
GPU 上算完 -> continues_on(CPU) -> CPU 后续
```

- 前半段 completing domain = GPU
- 后半段 completing domain = CPU
- 最外层 starting domain 可能来自 `sync_wait` 的 root env

没有这两分，跨上下文管道很难正确 lowering。

---

## 11. `indeterminate_domain` 是什么

当多个子 sender 的 domain 不一致、又无法合成共同 domain 时，会出现 `indeterminate_domain`。

它的策略是：

- 若所有候选 domain 对这次 transform 都表现得像 `default_domain`，就走默认
- 否则直接编译期炸：  
  `ERROR: indeterminate domains: cannot pick an algorithm customization`

这在 `when_all` 多路汇合时很常见：  
不能一边按 GPU 改写、一边按 CPU 改写，还假装有唯一答案。

## 12. 真实后端：`nvexec::stream_domain`

`nvexec` 是理解 domain 的最佳标本。

```cpp
struct stream_domain {
  template <sender_for Sender, class Tag = tag_of_t<Sender>, class Env>
    requires has_stream_transform<Sender, Env>
  static auto transform_sender(set_value_t, Sender&& sndr, Env const& env) {
    // 按算法 Tag 分发到 transform_sender_for<Tag>
    return structured_apply(transform_sender_for<Tag>{}, sndr, env);
  }

  template <class Tag, sender Sender, class... Args>
  static auto apply_sender(Tag, Sender&& sndr, Args&&... args) {
    return apply_sender_for<Tag>{}(sndr, args...);
  }
};
```

对 `then`：

```cpp
transform_sender_for<then_t> {
  // 若 child 是 stream-completing sender
  // 则替换成 nvexec 的 then_sender
  // 否则报：环境里没有 CUDA stream scheduler
}
```

于是用户仍然写：

```cpp
schedule(stream_sched) | then(f) | bulk(...)
```

框架在 connect 前自动把可 GPU 化的节点换成 stream 实现。

## 13. 你写业务代码时，到底会不会碰到 domain

### 大多数时候：不直接碰

你只需要：

- 选对 scheduler
- 写 `then/let/when_all/on/...`
- 让 attrs/env 自动携带 domain

### 你需要理解 domain 的场景

1. 看不懂为什么同一段 `then` 在 GPU/CPU 行为不同  
2. 自定义 scheduler/backend  
3. 编译错误出现 domain / transform_sender / indeterminate domain  
4. 想让自己的算法支持后端定制  
5. 读 `nvexec` / 自定义执行上下文源码

### 你真正要手写 domain 的场景

基本上只有：

- 你在实现新的执行后端
- 或你在给已有算法做特殊 lowering

普通应用开发者通常 **用 domain，而不是定义 domain**。

## 15. 用 6 句话把 domain 钉死

1. **Domain 是算法改写策略，不是执行器。**  
2. **它主要在 `connect` 前通过 `transform_sender` 工作。**  
3. **Completing domain 来自 sender attrs；Starting domain 来自 receiver env。**  
4. **Scheduler 常负责发布 domain，但两者职责不同。**  
5. **`default_domain` 负责默认行为；自定义 domain 负责 backend 特化。**  
6. **你写 `then`，框架借 domain 决定这是 CPU then 还是 GPU then。**

---

## 16. 一个帮助记忆的类比

把 sender 管道想成 SQL：

- 你写的是逻辑计划：`SELECT ... JOIN ... WHERE ...`
- optimizer/backend 会改写成物理计划：HashJoin / IndexJoin / GPU Join

在 stdexec 里：

- 你写的 sender 树 = 逻辑计划
- **domain = backend-specific lowering rules**
- scheduler = 最终执行设备/资源

所以 domain 难，是因为它处在“语言层”和“后端实现层”之间，不像 `then` 那样直观可见。
