你说得对。上次偏“桥怎么搭”，你真正想要的是：**为什么这两套东西在语义上本来就是同一类异步，所以可以互相当对方用**。

## 1. 先忘掉 API，只看“异步操作”是什么

无论是 awaitable 还是 sender，描述的都是同一件事：

> 现在还没结果；将来某个时刻会产生一个结局；在结局到来前，调用方可以挂起/去做别的事。

差别主要在**表达方式**：

| | Awaitable / 协程 | Sender / Receiver |
|---|---|---|
| 控制流 | 像同步代码：`co_await` 写“先 A 再 B” | 像组合子：`| then | when_all` |
| 启动 | 常在 `await_suspend` 附近开始推进 | 明确 `connect` 再 `start` |
| 结果怎么交 | `await_resume` 返回 / 抛异常 | `set_value` / `set_error` / `set_stopped` |
| 取消 | 语言没有一等“取消返回”，要额外协议 | 一等通道 `set_stopped` |
| 组合 | 靠 `co_await` 串起来 | 靠算法树组合 |

所以融入 execution 的关键不是“把协程语法塞进库”，而是：

> **两边都是“延迟的异步结果”的两种界面；只要结局语义能一一对应，就能互相当对方。**

## 2. 为什么“可以转换”：结局同构

异步操作最终只有有限几种结局。两边其实在说同一张表：

```text
成功拿到值     →  继续往下走，带着值
失败           →  失败路径
被取消/不再需要 →  取消路径（不是普通失败）
```

对应关系是**语义映射**，不是实现技巧：

```text
await_resume() 得到 T     ↔  set_value(T)     （void ↔ set_value()）
抛异常 / 异常结果         ↔  set_error(...)
“别再恢复我了，取消展开”  ↔  set_stopped()
```

一旦承认这张表，转换思路就很朴素：

### Awaitable → Sender

把 awaitable 看成一个还没启动的异步操作：

- **start**：去跑这个 awaitable（ready 就立刻完成，否则 suspend 等它）
- **成功 resume**：对 receiver `set_value`
- **异常**：`set_error`
- **取消协议触发**：`set_stopped`

于是 awaitable 能进 `when_all`、`sync_wait`、`spawn` 这些只认 sender 的世界。

### Sender → Awaitable

把 sender 看成“可以被 `co_await` 的东西”：

- **suspend**：`connect + start`
- **set_value**：resume，让 `await_resume` 交出值
- **set_error**：resume，让 resume 侧以异常形式呈现失败  
  （协程世界更习惯 try/catch，而不是三条回调）
- **set_stopped**：不要正常 resume 业务续体，走“取消展开”

于是你可以在协程里写控制流，同时复用整套 sender 算法和 scheduler。

## 3. 真正的设计意图：两种写法，一个异步内核

P2300 / stdexec 的核心抽象是 **sender/receiver 的完成模型**，不是协程。  
协程被接进来，是因为现实里两种写法都刚需：

1. **结构化组合**更适合 sender  
   并行、取消扇出、调度迁移、自定义后端（domain）——用算法树更清晰。

2. **业务控制流**更适合协程  
   分支、循环、局部变量、顺序逻辑——用 `co_await` 更自然。

所以 interop 的思路是：

```text
        ┌────────────────────────────┐
        │  统一的异步语义内核         │
        │  “将来完成：值/错/取消”     │
        └─────────────┬──────────────┘
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
   Sender 组合界面            协程/awaitable 界面
   (库/算法/调度/后端)        (人写业务顺序)
```

不是“协程实现了 execution”，也不是“execution 依赖协程”。  
是 **同一语义的两个前端**。

## 4. 为什么“能融入”，而不是硬焊

能自然融入，因为两边共享至少这四件事：

### （1）都是惰性描述，不是立刻执行

- sender：造出来不跑，`start` 才跑  
- 好的 task/awaitable 也常是 lazy（创建后先挂着，被 await/connect 才推进）

如果一边是“构造即开火”，一边是“描述后启动”，互操作会很别扭。  
execution 选择的是 **lazy async**，和现代 task 协程同向。

### （2）都把“操作对象”和“如何继续”分开

- sender + receiver：操作描述 vs 完成后的续体  
- awaitable + coroutine handle：可等待物 vs 恢复哪个协程

转换时只是在换“续体的形态”：

```text
receiver 的三个 set_*   ↔   resume / 抛错 / 取消展开
```

### （3）都需要上下文，不只是一个返回值

真实异步不只“算出 T”：

- 在哪个执行器上继续
- 取消令牌是谁
- 分配器、后端 domain …

sender 用 **env（receiver 侧上下文）** 和 **attrs（sender 侧属性）** 表达这些。  
协程用 **promise 暴露的上下文** 表达几乎同一类信息。

所以 promise 在概念上很像“长寿命的 receiver 环境提供者”：

```text
co_await sender
= 在“当前协程上下文”里启动这个 sender，
  并把三种完成翻译成协程续体
```

### （4）组合性要求可逆的边界

如果协程不能变成 sender，那：

- 协程写的子流程就进不了 `when_all` / `stop_when` / 线程池调度图

如果 sender 不能被 await：

- 业务一复杂就得手写 receiver，可读性崩掉

双向转换让边界可渗透：

```text
算法图里嵌协程任务，协程里又 await 算法图
```

这才是“融入”，不是单向适配器。

## 5. 转换时真正在做的“语义翻译”（思路层）

可以记成两句：

### Sender 当 awaitable

> “请把这个异步操作的三种完成，翻译成协程世界的继续/抛错/取消。”

### Awaitable 当 sender

> “请把这个可等待物的 resume/异常/取消，翻译成 receiver 的三种完成。”

中间没有新的异步理论，只是 **UI 层换皮**。

一个心智图：

```text
          值完成
           │
   ┌───────┼────────┐
   │                │
await_resume(T)   set_value(T)


          失败
           │
   ┌───────┼────────┐
   │                │
  异常            set_error


          取消
           │
   ┌───────┼────────┐
   │                │
不恢复业务续体    set_stopped
(取消展开)        (明确取消通道)
```

## 6. 不完美对齐的地方（所以是“融入”，不是“等同”）

正因为只是语义近似同构，有几处天然摩擦，这也解释了为什么需要额外约定：

1. **取消不是 C++ 协程一等公民**  
   sender 有 `set_stopped`；协程要额外的 `unhandled_stopped` 思路。  
   否则取消只能被伪装成异常，语义会脏。

2. **错误通道更宽 vs 异常更窄**  
   sender 的 `set_error` 可以是任意错误类型；协程侧通常收敛成异常模型。  
   await 一个 sender 时，error 常被“降维”成异常体验。

3. **多值完成 vs 单返回值**  
   sender 可以 `set_value(a,b,c)`；`co_await` 更像一个表达式值。  
   所以思路上要有“多值如何变成一个 await 结果”（打包/限制）的约定。

4. **结构化并发与帧寿命**  
   sender 的 opstate 寿命规则很硬；协程帧也有寿命。  
   互转时必须保证：操作完成前，续体/帧还活着。这是正确性条件，不是语法糖。

这些不阻碍融入，但说明：

> 互转保留的是“异步完成语义”，不是两种模型的所有细节表面。

## 7. 用“为什么需要它”收束

Awaitable 与 sender 能互相转换，是因为：

1. 它们描述的是**同一种东西**：延迟的、将来完成的计算  
2. 完成结果可以**三通道对齐**：值 / 错 / 取消  
3. 两边都区分**描述与启动**，都需要**上下文**  
4. execution 需要两种前端：  
   - sender：可组合的异步汇编  
   - 协程：可读的异步高级语言  

所以协程不是 execution 的外挂玩具，而是：

```text
execution 的异步语义
        ×
人类友好的控制流界面
```

一句话版：

> **Sender 是异步的“可组合数据流/运算子界面”，awaitable 是异步的“可挂起控制流界面”；因为完成语义同构，所以能互译，因而协程能自然进入 execution，而不是另起炉灶。**

如果你愿意，下一步我可以只画一张“同一段业务”的双写法对照（纯协程 vs 纯 sender vs 混合），完全不谈实现细节，专门练这种互译直觉。

先给结论，再拆开讲。

## 先给结论

1. **`set_stopped` 不是异常，也不会走 `await_resume`。**  
   它会让 awaiter 走 `unhandled_stopped()` 这条“取消展开”链，把取消往上层协程/receiver 传。

2. **通用 awaitable 并不“保存” sender 的 attrs。**  
   attrs 仍在原始 sender 上；await 时只是用 promise env 做 `transform_sender`，再用 receiver env 去 `connect`。

3. **想 `co_await sender`，promise 至少要能提供 env，并且实现 `unhandled_stopped()`；最好再继承 `with_awaitable_senders`。**

## 1. `set_stopped` 后，协程怎么衔接

### 1.1 三条完成通道在协程里不是对称的

| sender 完成 | awaiter 存什么 | 协程后续 |
|---|---|---|
| `set_value(...)` | result variant 存值 | resume 当前协程 → `await_resume` 返回值 |
| `set_error(e)` | 转成 `exception_ptr` | resume 当前协程 → `await_resume` rethrow |
| `set_stopped()` | **result 保持 valueless** | **不正常 resume 当前协程** → `unhandled_stopped()` |

关键点：取消不是“返回一个 stopped 值”，而是“当前 `co_await` 点之后的代码不再执行”。

### 1.2 通用路径：`as_awaitable(sender)` 的时序

```text
co_await sndr
  -> await_transform -> as_awaitable(sndr, promise)
  -> __sender_awaiter
  -> connect(sndr, special_receiver)
  -> await_suspend: start(opstate)

sender 某时刻:
  receiver.set_stopped()
    1) 不往 result 里写任何值  (valueless = stopped)
    2) 触发“完成通知” __done() / 返回 continuation
    3) continuation = __get_continuation()
         if result valueless:
              return unhandled_stopped(current_coro)
         else:
              return current_coro   // 正常 resume
```

源码语义就在 `__as_awaitable.hpp`：

- `set_stopped()`：result 保持空
- `__get_continuation()`：空 result 时走 `__coroutine_unhandled_stopped(continuation_)`
- `await_resume()` 断言 result 非空，所以 stopped 路径根本不该进这里

### 1.3 `unhandled_stopped()` 是什么

它是协程版的“取消 EH 表”。

```cpp
// 概念上
coroutine_handle<> promise::unhandled_stopped() noexcept;
```

含义：

- 当前协程在 `co_await` 点收到 stopped
- 不要 resume 到 `co_await` 后面
- 返回“接下来该 resume 谁”

常见实现：

```cpp
// with_awaitable_senders 提供的默认行为
coroutine_handle<> unhandled_stopped() const noexcept {
  return continuation_.unhandled_stopped(); // 丢给父协程
}
```

于是多层 task 会像这样展开：

```text
taskA
  co_await taskB
    co_await taskC
      co_await some_sender   // 这里 set_stopped

some_sender.set_stopped
  -> C 的 awaiter 调 C.promise.unhandled_stopped()
     -> 默认转给 B 的 continuation.unhandled_stopped()
        -> 再转给 A
           -> 直到某个边界把 stopped 变成 receiver.set_stopped()
              或 sync_wait/connect_awaitable 的边界处理
```

### 1.4 边界怎么“落地”成真正的 `set_stopped`

有两类边界：

**A. awaitable 被当成 sender connect 出去时**  
`__connect_awaitable` 的合成 promise：

```cpp
coroutine_handle<> unhandled_stopped() noexcept {
  set_stopped(receiver);
  return noop_coroutine(); // 不再往下 resume
}
```

所以：

```text
sync_wait(task()) / connect(awaitable, rcvr)
  内部如果取消展开到这层
  -> 对外部 receiver 调 set_stopped
```

**B. task 自己的最终边界**  
例如 `stdexec::task` / `exec::task` 在 parent 侧 awaiter 里，把 child 的 stopped 继续转给 parent，或在作为 sender 完成时输出 `set_stopped_t()`。

### 1.5 和异常路径对比（帮助建立直觉）

```text
set_error:
  像 throw
  resume 当前帧
  await_resume 里 rethrow
  可被 try/catch 接住

set_stopped:
  不像 throw
  不 resume 到 co_await 后面
  走 unhandled_stopped 链
  普通 try/catch 接不住
```

所以你不能写：

```cpp
try {
  co_await cancellable_sender;
} catch (...) {
  // 接不住 set_stopped
}
```

要处理取消，得靠：

- 上层 receiver 的 `set_stopped`
- `let_stopped` / `upon_stopped`
- 或者 task/scope 的取消语义边界

### 1.6 一个具体时间线

```cpp
task<int> foo(inplace_stop_token st) {
  // 假设这个 sender 会观察 stop token，并 set_stopped
  int v = co_await cancellable_work(st);
  co_return v + 1;   // stopped 时这行不会执行
}
```

```text
T0  foo 被 co_await / connect+start
T1  await_transform(cancellable_work)
T2  as_awaitable -> connect(sender, awaiter_receiver)
    awaiter_receiver.get_env() = foo.promise.get_env()
    其中通常能查到 stop_token
T3  start(opstate)
T4  外部 request_stop()
T5  sender 完成: set_stopped(awaiter_receiver)
T6  awaiter 发现 stopped:
    不调用 await_resume
    调用 foo.promise.unhandled_stopped()
T7  若 foo 被父协程 await:
      返回 parent.unhandled_stopped()
    若 foo 被 connect 到普通 receiver:
      边界处 set_stopped(receiver)
T8  foo 协程体从 co_await 之后不再继续
```

## 2. awaitable 如何表示 sender 的 attribute

### 2.1 先分清：attrs 不是 awaitable 的字段

在 stdexec 里：

- **sender attrs** = `get_env(sender)`
- **receiver/promise env** = `get_env(receiver)` / `get_env(promise)`

通用 `__sender_awaiter` **不会**把 sender attrs 拷进 awaiter 再对外暴露成“awaitable 的 get_env”。  
它做的是：

```text
await 前:
  transform_sender(sndr, get_env(promise))   // 可能按 domain 改写
  仍可读取 get_env(sndr) 上的 attrs 来做适配

connect 时:
  receiver.get_env() == get_env(promise)     // 运行时上下文
```

所以更准确的说法是：

> awaitable 是执行适配层；attrs 仍属于 sender 本体，不先被 awaitable“重编码成另一套属性对象”。

### 2.2 `as_awaitable` 实际怎么用到 attrs

`as_awaitable` 里有一步：

```cpp
// 伪代码
auto adapted = get_await_completion_adaptor(get_env(sndr))(sndr);
// 以及
transform_sender(sndr, get_env(promise));
```

也就是：

1. 先看 **sender attrs**（`get_env(sndr)`）  
   - 例如 completion behavior / await completion adaptor
2. 再用 **promise env** 做 `transform_sender`  
   - domain 改写、上下文相关定制
3. 最后 `connect` 时，运行时 queries 走 **promise env**

### 2.3 如果类型自己实现 `as_awaitable`，可以“带着语义走”

这是 attrs 间接保留的正道：

```cpp
struct my_sender {
  auto get_env() const noexcept {
    return prop{get_completion_scheduler<set_value_t>, sch_};
  }

  template <class Promise>
  auto as_awaitable(Promise& p) && {
    // 这里你仍然看得到自己的 attrs / sch_
    // 也可以看 get_env(p)
    return my_custom_awaiter{...};
  }
};
```

像 `exec::task` / `stdexec::task` 就走成员 `as_awaitable(ParentPromise&)`，在 awaiter 构造时：

- 从 parent env 取 start scheduler / stop token
- 建立 child context
- 自己的 sender attrs（若作为 sender）仍可单独通过 `task.get_env()` 提供

### 2.4 awaitable 作为 sender 时，completion signatures 怎么来

当 awaitable 反向被当成 sender：

```text
completion_signatures_of(awaitable) ≈
  set_value_t(await_result_t<...>)
  set_error_t(exception_ptr)
  set_stopped_t()
```

注意：

- 这是从 **await 结果类型 + 异常/取消协议** 推的
- **不是**自动继承原 sender 的全部 attrs
- 原 sender 的 `get_completion_scheduler` 等，不会因为包了一层通用 awaiter 就自动变成 awaitable 的 attrs

### 2.5 一张对照图

```text
原始 sender S
  attrs = get_env(S)
    - completion_scheduler
    - completion_domain
    - completion_behavior
    - ...

co_await S  (通用路径)
  awaitable/awaiter A
    - 不对外宣称自己等于 attrs(S)
    - 内部 connect 时:
        env = get_env(promise)
    - 启动前可能:
        transform_sender(S, env(promise))
        读取 attrs(S) 做适配

若 S 有成员 as_awaitable:
  自定义 awaiter 可以显式保留/解释 attrs
```

**记忆法：**

- attrs 描述“这个操作完成后像什么”
- env 描述“现在在什么上下文里跑”
- awaitable 负责 suspend/resume 机械过程  
  它消费 attrs/env，但不默认重发布 attrs

## 3. 想 `co_await sender`，promise 要满足什么

### 3.1 最低硬约束

#### A. 必须能提供 `unhandled_stopped()`

这是最硬的一条。

`as_awaitable` 对通用 sender 要求：

```cpp
// 概念上
requires (Promise& p) {
  { p.unhandled_stopped() } -> convertible_to<coroutine_handle<>>;
};
```

`__coroutine_handle` 也写死了：

> Coroutine promises used with senders must implement `unhandled_stopped()`  
> 否则 stopped 展开到这里会 `terminate()`

所以：没有 `unhandled_stopped` 的普通 promise，不能安全 `co_await sender`。

#### B. 最好能 `get_env()`

严格说，很多路径通过 `env_of_t<Promise&>` 取 env。  
promise 若没有 queryable env，复杂 sender（要 stop token / scheduler / allocator）会编不过或行为残缺。

最低实用形态：

```cpp
struct promise {
  auto get_env() const noexcept {
    return env{
      prop{get_stop_token, stop_token_},
      // 可选:
      // prop{get_scheduler, sch_},
      // prop{get_start_scheduler, sch_},
    };
  }
};
```

#### C. 应该有 `await_transform` 把 sender 转成 awaitable

最省事：

```cpp
struct promise : stdexec::with_awaitable_senders<promise> {
  // 继承来的:
  // await_transform(x) -> as_awaitable(x, *this)
  // unhandled_stopped() -> continuation.unhandled_stopped()
  // set_continuation(...)
};
```

如果你手写：

```cpp
template <class X>
auto await_transform(X&& x) {
  return stdexec::as_awaitable(std::forward<X>(x), *this);
}
```

### 3.2 推荐的完整 promise 清单

| 成员 | 必要性 | 作用 |
|---|---|---|
| `unhandled_stopped()` | **必须** | 衔接 `set_stopped` |
| `get_env()` | **强烈必须** | 给被 await 的 sender 提供 stop/scheduler 等 |
| `await_transform` / `with_awaitable_senders` | **强烈必须** | `co_await sender` 入口 |
| `set_continuation` / `continuation` | 嵌套 task 时必须 | 取消和 final_suspend 回到父协程 |
| `initial_suspend` / `final_suspend` | task 语义需要 | lazy 启动、完成后 resume parent |
| `unhandled_exception` | 建议 | 把异常收成 error 通道或存起来 |
| `return_value` / `return_void` | task 需要 | 对应 `set_value` |

### 3.3 一个最小可用骨架

```cpp
struct my_promise : stdexec::with_awaitable_senders<my_promise> {
  my_task get_return_object();
  std::suspend_always initial_suspend() noexcept { return {}; }
  auto final_suspend() noexcept {
    struct A {
      bool await_ready() noexcept { return false; }
      coroutine_handle<> await_suspend(coroutine_handle<my_promise> h) noexcept {
        return h.promise().continuation().handle();
      }
      void await_resume() noexcept {}
    };
    return A{};
  }

  void return_void() {}
  void unhandled_exception() { /* store / rethrow policy */ }

  // with_awaitable_senders 已提供:
  // - await_transform -> as_awaitable
  // - unhandled_stopped -> continuation.unhandled_stopped()

  auto get_env() const noexcept {
    return stdexec::prop{stdexec::get_stop_token, token_};
  }

  stdexec::inplace_stop_token token_{};
};
```

### 3.4 额外语义约束（不只是“有没有这个函数”）

1. **`unhandled_stopped` 必须 noexcept，并返回有效可 resume 的 handle**  
   返回 `noop_coroutine()` 也可以，表示“到此为止”。

2. **value 通道要可 await 化**  
   通用 `as_awaitable` 期望 value 侧能收成 0/1 个值（多值会打成单值形式）。  
   不能稳定算出 value 类型时，sender 与该 promise env 不兼容。

3. **sender 必须在 `env_of_t<Promise&>` 下是 `sender_in`**  
   也就是 completion signatures 在这个 env 下可计算。

4. **stop token 要真的传到 sender**  
   只实现 `unhandled_stopped` 不够；若 `get_env()` 不提供 `get_stop_token`，很多 cancellable sender 根本观察不到取消请求。

5. **sticky task 还要 start scheduler**  
   `exec::task` 这类会要求 parent 能提供 `get_start_scheduler`，以便 affinity / `continues_on`。

## 4. 把三问串成一条因果链

```text
你写:
  co_await sndr;

promise 负责:
  await_transform -> as_awaitable(sndr, promise)
  get_env()       -> 成为 awaiter_receiver 的 env
  unhandled_stopped() -> 处理 set_stopped

as_awaitable 负责:
  读取 attrs(sndr) 做必要适配
  用 env(promise) transform/connect
  把 set_value/error/stopped 映射到 resume/throw/unhandled_stopped

结果:
  value  -> 回到 co_await 下一行
  error  -> 以异常形式进入协程
  stopped-> 跳过后续协程体，沿 unhandled_stopped 往上取消
```

## 5. 最短记忆版

- **`set_stopped` = 取消展开，不是 resume。**
- **衔接点叫 `promise.unhandled_stopped()`。**
- **awaitable 默认不重发布 sender attrs；attrs 仍在 sender，await 时被读取/用于 transform。**
- **`co_await sender` 的 promise 三件套：**
  1. `unhandled_stopped()`
  2. `get_env()`
  3. `await_transform` / `with_awaitable_senders`
