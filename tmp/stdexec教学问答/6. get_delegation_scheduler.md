先给结论，再用一个完整例子把链路走完。

## 结论

`sync_wait` **自己不会主动“调用算法用 delegation”**。  
它做的是：

1. 在调用线程上建一个内部 `run_loop`
2. 把这个 `run_loop` 的 scheduler 放进 receiver 的 env
3. 对这三个 query 都回答同一个东西：

```cpp
get_scheduler
get_start_scheduler
get_delegation_scheduler
  -> 都返回 run_loop::scheduler
```

4. 然后 `start(op)`，并在本线程 `run_loop.run()` 抽任务

所以：

> `get_delegation_scheduler` 是 `sync_wait` 暴露给下游 sender 的“回到等待线程继续推进”的入口。

下游如果写：

```cpp
continues_on(get_delegation_scheduler(env))
// 或
schedule(get_delegation_scheduler(env))
```

就会把 continuation 投回 `sync_wait` 正在驱动的那个 `run_loop`，由等待线程自己执行，从而避免死锁。

## 1. 源码里它怎么接上的

### 1.1 `sync_wait` 的 env

```cpp
struct __env {
  template <__one_of<get_scheduler_t,
                     get_start_scheduler_t,
                     get_delegation_scheduler_t> _Query>
  auto query(_Query) const noexcept -> run_loop::scheduler {
    return __loop_->get_scheduler();
  }

  run_loop* __loop_ = nullptr;
};
```

receiver 的 `get_env()`：

```cpp
auto get_env() const noexcept -> __env {
  return __env{&__state_->__loop_};
}
```

### 1.2 `sync_wait` 主流程

```cpp
// 简化版
__state local;
optional<tuple<...>> result;

auto op = connect(sndr, receiver{&local, &result});
start(op);          // 启动异步图
local.__loop_.run(); // 本线程开始抽队列，直到 finish()
```

完成时 receiver：

```cpp
set_value(...) {
  values->emplace(...);
  state->loop.finish();  // 通知 run_loop 可以结束
}
```

### 1.3 `run_loop` 做什么

```text
run():
  while (!finishing)
    wait_for_item()
    execute_all()

finish():
  finishing = true
  塞一个空任务把等待线程叫醒
```

也就是说：`sync_wait` 的调用线程不是纯 `sleep`，而是变成了一个**本地事件循环线程**。

---

## 2. 为什么需要 `get_delegation_scheduler`

经典危险场景：

```text
主线程调用 sync_wait
  -> 需要等结果
  -> 但后续 continuation 又要求“回到主线程”
  -> 如果主线程只是死等、不跑队列
  -> continuation 永远上不了主线程
  -> 死锁
```

`sync_wait` 的解法是：

```text
主线程不是死等，
而是 run_loop.run() 主动执行被投递回来的任务。
```

`get_delegation_scheduler` 的意义就是告诉下游：

> 你如果要把工作委托回“正在等待并负责推进”的那条执行线，请投到这个 scheduler。

在 `sync_wait` 场景里，这个 scheduler 就是内部 `run_loop`。

---

## 3. 一个详细具体例子

### 场景

1. 主线程 `sync_wait`
2. 先 hop 到线程池做耗时计算
3. 再 hop 回 `sync_wait` 所在线程做收尾
4. 最终在主线程拿到结果

### 代码

```cpp
#include <stdexec/execution.hpp>
#include <exec/static_thread_pool.hpp>
#include <iostream>
#include <thread>

namespace ex = stdexec;

int main() {
  exec::static_thread_pool pool{2};
  auto pool_sch = pool.get_scheduler();

  auto snd =
      // A. 先读 env 里的 delegation scheduler
      //    在 sync_wait 下，它就是内部 run_loop 的 scheduler
      ex::read_env(ex::get_delegation_scheduler)
    | ex::let_value([pool_sch](auto home_sch) {
        std::cout << "build pipeline on thread "
                  << std::this_thread::get_id() << "\n";

        return
            // B. 去线程池计算
            ex::schedule(pool_sch)
          | ex::then([] {
              std::cout << "compute on pool thread "
                        << std::this_thread::get_id() << "\n";
              return 21;
            })

            // C. 关键点：回到 sync_wait 的等待线程
          | ex::continues_on(home_sch)
          | ex::then([](int v) {
              std::cout << "finish on home thread "
                        << std::this_thread::get_id() << "\n";
              return v * 2;
            });
      });

  // D. 主线程同步等待
  auto [ans] = ex::sync_wait(std::move(snd)).value();
  std::cout << "answer=" << ans
            << " on thread " << std::this_thread::get_id() << "\n";
}
```

### 你大概会看到类似输出

```text
build pipeline on thread 1
compute on pool thread 2
finish on home thread 1
answer=42 on thread 1
```

关键点：

- `home_sch` 不是线程池
- `home_sch` 是 `sync_wait` 内部 `run_loop` 的 scheduler
- 所以 `continues_on(home_sch)` 会把最后一步投回主线程，并由主线程的 `run_loop.run()` 执行

---

## 4. 这个例子在运行时逐步发生了什么

### Step 0：进入 `sync_wait`

主线程 Tmain：

```text
创建 local_state.loop
创建 receiver.env 里挂上 &loop
connect(snd, receiver)
start(op)
loop.run()   // Tmain 开始当事件循环
```

此时 env 已具备：

```cpp
get_delegation_scheduler(env) -> loop.get_scheduler()
```

### Step 1：`read_env(get_delegation_scheduler)`

这个 sender 从 receiver env 读 query：

```text
home_sch = env.query(get_delegation_scheduler)
         = run_loop::scheduler
```

于是 `let_value` 得到 `home_sch`，开始构造后续 pipeline。

### Step 2：`schedule(pool_sch) | then(...)`

工作被投到线程池：

```text
Tpool:
  print "compute on pool thread"
  return 21
```

现在值在池线程上。

### Step 3：`continues_on(home_sch)`

`continues_on` 的语义是：

> 前驱在哪完成都行；  
> 完成后 hop 到目标 scheduler，再把值转发给下游。

目标是 `home_sch = run_loop.scheduler`，所以它会：

```text
schedule(home_sch)  // 往 run_loop 队列塞一个任务
```

### Step 4：主线程 `run_loop` 抽到这个任务

Tmain 正在：

```text
loop.run():
  wait_for_item()
  execute task
```

于是执行：

```text
then([](int v){ return v*2; })   // 在 Tmain 上
```

打印：

```text
finish on home thread ...
```

### Step 5：最终完成 `sync_wait`

下游最终 `set_value(42)` 打到 `sync_wait` 的 receiver：

```text
result = optional{tuple{42}}
loop.finish()
```

`run()` 退出，`sync_wait` 返回 `42`。

## 5. 时序图

```text
Tmain (sync_wait)                  Tpool
-----------------                  -----
create run_loop
connect + start
run_loop.run()  --------------------\
                                     \
read_env(get_delegation_scheduler)    \
  home_sch = loop.scheduler           \
                                      \
schedule(pool)  -------------------->  compute(21)
                                      /

  push task into run_loop

loop.finish()
run() 返回
sync_wait 得到 42
```

## 6. 如果没有 delegation，会发生什么

把例子改坏：

```cpp
// 错误直觉：我想“回到主线程”，但没有可驱动的 home scheduler
auto snd =
    ex::schedule(pool_sch)
  | ex::then([] { return 21; })
  | ex::continues_on(/* ??? 主线程普通阻塞点，没有 loop ??? */)
  | ex::then([](int v){ return v*2; });

auto [ans] = ex::sync_wait(std::move(snd)).value();
```

如果主线程只是：

```text
提交工作
然后 condvar.wait() 死等结果
自己不跑任何队列
```

而 continuation 又要求回主线程，就会：

```text
池线程算完了，想投回主线程
主线程在死等，不处理投递
结果永远出不来
```

`sync_wait` 通过：

1. 自带 `run_loop`
2. 用 `get_delegation_scheduler` 暴露它

把这个问题消掉。

## 7. 为什么叫 “delegation”，不是 “home thread scheduler”

因为通用语义是 **进度委托**，不特指“主线程”：

```text
当前执行者可能要等待
但它自己未必还能继续推进相关工作
于是把“推进责任”委托给另一个 scheduler
```

在 `sync_wait` 中：

- 等待者：调用线程
- 被委托对象：该线程上的 `run_loop.scheduler`
- 被委托的工作：需要回到等待上下文的 continuation

所以文档才说：

> 这让 `continues_on` 能安全回到 `sync_wait` 的调用线程。

---

## 8. 和 `get_scheduler` 的关系（在 `sync_wait` 里）

在 `sync_wait` 的 env 中，这三者目前相同：

```cpp
get_scheduler(env)
get_start_scheduler(env)
get_delegation_scheduler(env)
  -> 都是同一个 run_loop::scheduler
```

这不代表三者概念相同，只代表 `sync_wait` 这个消费端把它们都指向了自己的 loop。

直观分工仍是：

| query | 在 sync_wait 里实际值 | 概念角色 |
|---|---|---|
| `get_scheduler` | run_loop.scheduler | 当前默认执行上下文 |
| `get_start_scheduler` | run_loop.scheduler | 启动相关上下文 |
| `get_delegation_scheduler` | run_loop.scheduler | 进度可委托到哪里 |

## 9. 另一个更“委托味道”的写法

不一定非要 `continues_on`，也可以显式：

```cpp
ex::read_env(ex::get_delegation_scheduler)
| ex::let_value([](auto dsch) {
    return
        ex::schedule(dsch)
      | ex::then([] {
          // 这段保证跑在 sync_wait 的 run_loop 上
          return 1;
        });
  });
```

这和 `continues_on(dsch)` 一样，都是在说：

> 把后续工作委托给 sync_wait 正在驱动的那个 scheduler。

## 10. 最小记忆版

1. `sync_wait` = `connect + start + 本线程 run_loop.run()`
2. 它把 `run_loop.scheduler` 放进 env
3. `get_delegation_scheduler(env)` 读到的就是这个 scheduler
4. 下游用它把 continuation 投回等待线程
5. 等待线程靠 `run_loop` 执行这些任务，最终 `finish()` 并返回结果

一句话：

> `sync_wait` 不是靠“死等”完成异步图，而是靠“边等边驱动自己的 loop”；  
> `get_delegation_scheduler` 就是把这个 loop 的入口交给下游，让它们能把工作安全委托回来。
