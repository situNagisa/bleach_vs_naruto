# 设计一个每帧重建的任务图

每帧构建一张任务图，跑完，销毁；下一帧从零再建。基于 stdexec。
先只谈设计——这东西应该长成什么样、为什么，不要写实现代码。

## 角色

- **render**（vulkan）是一个 entity，负责 render begin / render end /
  **在每帧末尾等 fence**（不是在开头等上一帧的）
- **entity** 是一个 concept，不是基类。每个 entity 由不同的开发者写，
  默认形态就是一个纯计算任务
- 需要跟 render 同步的 entity：算完 → 在 render begin 之后录制命令 →
  在 fence 等待之后清理本帧资源
- **main** 知道所有具体 entity 类型：收集 entity、构图、执行、循环

## 硬约束

1. 图的形态、扇出、扇入、先后关系全部由 stdexec 表达。不要自己写调度器、
   拓扑排序、前驱计数、完成回调派发
2. 每帧重建整张图，单次发射
3. **不给非 render 的 entity 引入任何 render 概念**。纯计算 entity 的代码里
   不该出现 renderer、不该出现"节点""图"以外的东西。这一条要能机器检查
4. entity 跟 render 的同步由它们自己完成。main 里不许有任何针对某个具体
   entity 的特殊处理——加一个 entity 不改 main 的逻辑
5. **entity 列表本身是动态的**：运行期能增删，能插件化。但"A 依赖 B"这条边
   要保持具体类型直连，不许退化成字符串 / tag / 类型 id 查表

## 设计必须回答的问题

按这些问题组织你的设计，每条都要给出机制和取舍：

1. 图用什么表达？"某个节点被多个下游共享"和"等一批节点全部完成"分别对应
   stdexec 的哪个设施？
2. 一个 entity 怎么拿到"本帧的 renderer 状态"，而 main 完全不参与撮合？
3. 谁先注册、谁后注册，为什么可以无所谓？render end 要等的那批录制节点，
   名单是**什么时候**被读的？这个时机为什么是安全的？
4. 录制者集合每帧不同（有 entity 本帧不可见、有插件中途加入）。
   render end 怎么等一个**元素个数运行期才知道**的集合？
5. 每帧的状态住在哪个对象上？帧与帧之间的隔离靠纪律（记得清空）还是靠结构
   （上一帧的对象已经不存在）？
6. 异常和取消：一个录制者抛异常、或者上层取消整帧时，
   fence 等待和 slot 资源回收怎么保证一条都不漏？
7. entity 列表动态化之后，"我依赖的 entity 本帧不在场"是在什么时刻、
   以什么形式被发现的？跟静态列表相比失去了什么？
8. 哪些错误这个设计**抓得到**（成环、迟到注册、缺失依赖），
   哪些**抓不到**？抓不到的老实列出来，别当成抓得到。
