## 二、你的模型，我先精确重述 + 补一个洞

你给的三条：
- keyframe = `(1 个 renderable, 帧属性)`
- timeline = `[keyframe, keyframe, …]`
- **timeline 本身也是 renderable** ⇒ 于是 keyframe 里能塞 timeline ⇒ **递归/嵌套**（就是 Flash 的 MovieClip 套 MovieClip）。

这个递归非常干净，我完全认同它作为骨架。但有一个洞：**Flash 的一帧其实是"多图层同时显示"**，你却限制"一个关键帧只含一个 renderable"。这不是矛盾，但需要一个**空间合成节点**来补（见 §四-A）。

## 三、核心 reframe：一个实体一个 render task，树内部是"纯求值"

这是让你的模型和 render-task 协程模型兼容的**唯一关键动作**——把两件事分开：

- **缝（纯，无 GPU、无协程）**：`evaluate(node, t) → 该时刻的单帧合成`。timeline / keyframe / group 全活在这里，是 t 的**纯函数**。这**就是** §3 说的"给定 t → 单帧参数"，只是做成了可递归的。
- **适配器（= renderable / render task）**：`render(root, global)` = **一个** render task，每帧：取 t → `evaluate(root, t)` → 把结果画进 secondary command buffer。

于是：

| 节点被用在哪                                         | 走哪条路                                | 代价                                        |
| ---------------------------------------------- | ----------------------------------- | ----------------------------------------- |
| **根**（entity 直接 spawn 的那个）                     | CPO `render(root, global)`，展开成适配器协程 | 重（own backend，循环，收尾）——但**每个 entity 只有一个** |
| **嵌套**（keyframe 里的子 timeline / group / sprite） | `evaluate(child, t)`，被父级就地求值        | 廉价（纯数据递归）                                 |

**这样 §3 的缝被完整保住**：`evaluate` 纯粹不碰渲染；协程适配器才碰 GPU。"timeline 是 renderable"这句话，落在**根适配器**上成立；嵌套复用同一棵树但走 evaluate。**整棵树只有一个长命协程**，不是每个节点一个协程——这点和 render-task.md 完全吻合。

> 换句话说：你说的"renderable"其实同时指两个东西——引擎层的 `renderable`（粗、协程、每 entity 一个）和动画层的"2D 可绘节点"（细、纯、可组合）。它们**只在根处经适配器相接**。承认这个二义、并让根适配器当桥，是整个设计能自洽的支点。

## 四、逐件拆开讨论

### A. 节点词汇（建议的最小完备集）

| 节点                        | 作用                                                    | 是不是 renderable            |
| --------------------------- | ------------------------------------------------------- | ---------------------------- |
| **leaf**（sprite / 自定义） | 真正出像素                                              | 是                           |
| **group**                   | 同一时刻画**多个**子节点（空间/图层合成），各带局部变换 | 是                           |
| **timeline**                | 按播放头 t **选**子节点（时间合成）                     | 是                           |
| **keyframe**                | `(renderable, 帧属性)`——timeline 的元素                 | 否（是 timeline 的内部条目） |

group 是补上"Flash 多图层"那个洞的最小手段：`一个关键帧一个 renderable` 依然成立——要同屏多图层，那个 renderable 就是个 group。一个英雄 = `timeline{ 招式们 }`，每个招式 = `timeline{ 逐帧 pose }`，每个 pose = `group{ 身体、武器、特效 }`。timeline 管时间、group 管空间，两者都是 renderable，递归自由。

### B. 合成机制 = 变换/颜色栈（就是个 2D scene graph）

父级要能给子级**叠**变换和 tint（Flash 的嵌套 MovieClip 就是矩阵相乘）。做法是经典的 `push(transform,tint) → 画子级 → pop`。**推论**：keyframe 里的 renderable 必须暴露"可被父级后乘变换/着色"的形态——也就是**它得通过一个 2D context 画**，而不能是已经烤死的裸 Vulkan 命令（裸命令没法被父级再变换）。这直接决定了下一条。

### C. GPU 资源归属：一个 2D backend own，节点全是廉价数据

- 由 **一个 2D sprite backend** own 共享 pipeline + 顶点/索引 buffer + 批处理，它负责把累积的 quad 录进 secondary command buffer。这就是 render-task.md 里那个"重"的协程角色。
- 节点树全是**廉价数据**（texture handle + 变换 + 属性），随便嵌套。
- env 现在是**裸 Vulkan**，所以这个 2D 设施得**动画框架自建**——而这恰恰对：动画系统是"游戏衍生物、可被玩家整套替换"，它自带自己的 2D 绘制层完全合理，引擎核心不该知道 sprite 是什么。

于是"一个英雄动画 = 一个 render task = (2D backend + 节点树)"，落进 render-task 模型严丝合缝。

### D. 时间来源 / 播放头（这条最容易踩 §2）

**timeline 绝不自己走时钟**——它是 t 的纯函数，t 由外部喂：

- **权威动画**（招式当前帧）：t = 快照里的招式进度，sim 按 tick 推（§2 的"极轻时间线推进器"）。渲染只读快照 + 插值。
- **装饰动画**（待机呼吸、UI、纯特效）：t = 渲染时钟累积，随便跑。

嵌套 timeline 的**局部时间**有个分叉（见 §五-2）：纯映射 vs 有状态播放头。

### E. 帧属性集合（建议）

`transform`（2D 仿射：位/缩/旋/斜）、`color`（tint + alpha）、`blend`、`duration`（这帧保持几 tick）、`tween-to-next`（缓动曲线）或 `hold`、`layer/z`（group 内叠序）、`具名钩子引用`（§3 的"少量具名 C++ 钩子"，注意是**具名引用**不是内联 lambda，否则没法序列化）。

### F. 补间 vs §2 插值 / 离散化（格斗手感）

Flash 的 tween = 关键帧间插值，正好接上 §2"渲染做插值 + 帧离散"。建议**逐属性可离散**：

- **精灵 / clip 索引 = stepped（保持到下一关键帧）**——格斗游戏精灵是**硬切**不是淡入淡出；
- **transform / alpha = tween（连续插值）**——位置/缩放平滑。

Flash 本身就是这个语义。要不要这么细拆是个分叉（§五-4）。

### G. 表现 vs 玩法的边界（我认为最重要的一条）

Flash timeline 本质是**表现结构**。玩法帧数据（startup/active/recovery、逐帧 hit/hurt box、取消窗口）是**权威**的，得进 sim / 快照。**强烈建议两者分成平行结构、共享同一条时间轴**：编辑器可以同屏画（Fighter-Factory 风格），但表现树里**不混**权威数据。理由：表现 timeline 可能在渲染时钟自由跑，权威数据绝不能跟着渲染跑——否则 §2 的确定性/联网就破了。

### H. 序列化 / 编辑器往返（§4 的初衷）

节点类型是**小而封闭的集合**（leaf/group/timeline/keyframe），编辑器认得、能存能读；钩子是具名引用；手写英雄**整枝绕开**（代码即结构，符合 §4"手写英雄绕开它"）。这也是为什么 §三 我坚持"节点是纯数据 + evaluate"而不是"每节点一个协程"——协程没法序列化，纯数据树可以。

## 五、需要你拍板的分叉（每个附我的建议）

1. **keyframe 里的 renderable 收多重的？** 只收轻量 2D-drawable，还是也允许塞"重的引擎 renderable（自带协程/pipeline）"？
   → **建议只收轻量**。重的走"自定义 leaf（通过 2D context 画）"或整枝绕开 Flash 树。允许塞重协程会把"timeline 管子节点生命周期"这个大坑挖开（启停 or 保活+门控），不值得。

2. **嵌套 timeline 的局部时间：纯映射 vs 有状态播放头？**
   → **建议默认纯映射**（`local_t = f(parent_t)`，offset + 可选 loop 取模），确定性好、天然可快照/联网。确实需要 `gotoAndPlay`/中断分支这类有状态播放头时，那份状态按**状态二分**入位：权威→ECS 组件，装饰→协程局部（和你 memory 里的二分一致）。

3. **表现 / 玩法：分离平行结构（建议）还是统一 timeline 再切片？**
   → **建议分离**。统一虽好看，但每帧求值都得切"这块进 sim / 这块进 render"，复杂且易错。

4. **补间粒度：逐属性可离散（精灵 step / transform tween）要不要做？**
   → **建议要**，这是格斗手感的核心，且成本低。

5. **要不要引入 group 节点？**
   → **建议要**，否则"一个关键帧一个 renderable"没法表达多图层。
