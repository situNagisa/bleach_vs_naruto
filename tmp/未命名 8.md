我挑了两个最小的情形，把 `connect` 和 `start` 的每一步都走了一遍。**情形 A** 是往 buffer 里填数，再让 CPU 读回来，没有 swapchain，只看 GPU 和 CPU 之间怎么往返。**情形 B** 是 acquire、clear、present，专门看 swapchain 的 binary semaphore 和 present 这类队列级操作。推演中发现的细节我用 **【发现 N】** 标出来，最后汇总。

**情形 A：fill 再 readback**

```
auto s = stdexec::schedule(gfx)
       | vk::record([&](vk::encoder& e) { return e.fill(buf, 0xABCD); })   // 值：gpu_ref<buffer>
       | stdexec::then([](auto r) { return r[0]; });
auto [x] = stdexec::sync_wait(std::move(s)).value();
```

**先解决一个问题：encoder 从哪里来？**

标准 `then(f)` 调用的是 `f(vs...)`，拿不到 encoder。如果用 domain 把 `then` 改写成 `f(enc, vs...)`，完成签名的推导会在改写之前就失败，而且"同一个 `then` 有两种签名"本身就很混乱。

**【发现 1】** 录命令要用专门的 `vk::record(f)`，不要去改写 `then`。encoder 不经过值传递，而是由下游放进 **receiver 的 env** 里，上游通过查询 `get_encoder(env)` 拿到。

**【发现 2】这是整个推演里最关键的一条：GPU sender 什么时候完成，由它的 receiver 的 env 决定。**

- env 里**有** encoder：在"录制时"完成，意思是命令流里的一个位置，传出去的值是 `gpu_ref`（句柄）。
    
- env 里**没有** encoder：这个 sender 自己成为边界，负责 submit 并等 GPU 跑完，**GPU 真的做完之后**才完成，传出去的值变成 CPU 可用的 `host_ref`。
    

P2300 本来就允许完成签名依赖 env（`get_completion_signatures(sndr, env)`），所以这不是什么 hack。

**【发现 3】默认行为是安全的。** 会转发 env 的适配器（`then`、`let_value`）会自然地"跟着上游待在录制时"；不转发 env 的适配器（`split`、`start_detached`、`when_all` 内部等）会退化成"GPU 同步之后在 CPU 上继续"。**语义始终正确，最多只是慢一些。**

这样也回答了你最初的问题：`then` 不需要特殊处理。它总是"在前驱完成时执行"，前驱是哪一种完成，它就跟着是哪一种时间。

**【发现 4】命令缓冲是从最下游的 GPU 算子那里借来的。** 边界就是最靠下游的那个 GPU 算子，这和 sender 连接的方向（receiver 往上游传）天然一致。录制顺序等于上游 start 的顺序，也就等于数据流的顺序。

**start 阶段**

1. `sync_wait` 启动 `then`，`then` 启动 B。**B 先调用** `**vkBeginCommandBuffer**`，再启动上游。
    
2. `schedule` 同步调用 `set_value` 通知 B 的内部 receiver，随后 `f(enc)` 执行，录入 `vkCmdFillBuffer`。encoder 记下 buf 的状态为 `{transfer, transfer_write}`。
    
3. 因为 B 的下游是 CPU，B 要做这些事：
    

- 录入 barrier：transfer_write 到 host_read；
    
- `vkEndCommandBuffer`；
    
- **加队列锁，分配 N = ++counter，然后 submit 并 signal(timeline, N)，再解锁**；
    
- 调用 `reactor.register(timeline, N, &B)`。
    

4. `start` 返回，`sync_wait` 的 run_loop 进入睡眠。
    
5. reactor 线程上 `vkWaitSemaphores` 返回，B 接着：
    

- 如果内存不是 coherent，调用 invalidate；
    
- 回收命令缓冲；
    
- 调用 `set_value(then 的 receiver, host_ref)`，**这时** `**g**` **在 reactor 线程上执行**。
    

**【发现 5】** timeline 的值必须**在队列锁里、submit 之前**分配。同一个 semaphore 的 signal 值必须按提交顺序严格递增。如果先分配 N、N+1，而两个线程提交的顺序反了，就违反了规范。

**【发现 6】** 队列本身需要外部同步（`vkQueueSubmit`），所以每个队列都要一把锁，或者一个串行化的提交器。

**【发现 7】** 续体默认跑在 reactor 线程上（和 io_uring 的 completion 一个性质）。用户代码一旦阻塞，就会拖住所有 GPU 完成的通知。所以边界完成时，应该调度到 env 里的 `get_scheduler` 上，或者要求用户显式写 `continues_on`。

**【发现 8】** reactor 要用 `waitAny` 同时等多个队列的 timeline，但 `vkWaitSemaphores` **无法被打断**。当需要登记新的等待时，得额外准备一个"唤醒用"的 timeline semaphore，由 CPU 调 `vkSignalSemaphore` 把 reactor 叫醒。好在同一个队列上的值单调递增，所以只有新增队列或者 reactor 空闲时才需要唤醒。

**【发现 9】** 停止请求（stop）只能在 submit 之前生效。submit 之后即使收到停止，也必须等 GPU 做完才能 `set_stopped`，因为命令缓冲和资源都在算子状态里。**错误的完成（set_error）同理**，这就是你现在代码里 present 失败后先 `_wait_fence` 再 throw 的原因。

**情形 B：acquire、clear、present**

```
vk::acquire(swapchain)                                   // CPU 完成：swapchain_image
  | vk::record([](vk::encoder& e, vk::swapchain_image img) {
        e.clear(img, color);                              // 用 vkCmdClearColorImage，最简单
        return img;
    })
  | vk::present(swapchain)
  | stdexec::then([] { /* 帧结束 */ });
```

**acquire**

acquire 是一个 CPU 操作，而且会阻塞。可以用 `timeout = 0` 加重试，或者放到专门的线程上做。它完成时给出 `swapchain_image{index, VkImage, pending = image_available 这个 binary semaphore}`。

**【发现 10】带着 binary semaphore 的值必须只能移动、不能复制（仿射类型）。** 一个 binary signal 只能被一次 wait 消费。要是被 `split` 复制出两份，就会被 wait 两次。用 move-only 类型，`split` 只能给出 const 引用，交出 semaphore 需要右值，这样在编译期就能拦住。

**record**

lambda 拿到 `img` 之后，semaphore 该在什么时候变成 wait？wait 需要一个 `stage_mask`，而这个值取决于这张 image **第一次被怎么用**：clear 对应 transfer，作为 attachment 对应 color_attachment_output。

**【发现 11】"等待 semaphore"和"插 barrier"是同一个机制。** 值里带着的是"未满足的依赖"，也就是 `{semaphore 或同一命令缓冲里的某个位置, 上一次的 stage/access/layout}`。encoder 在第一次访问这个资源时统一处理：跨 submit 的依赖生成 wait semaphore，同一个命令缓冲里的依赖生成 barrier，同时做 layout 转换（这里是 undefined 到 transfer_dst）。**render graph 的状态跟踪就是从这里开始的**，情形 A 里的 fill 加 host barrier 也是它的一个特例。

**present**

`vkQueuePresentKHR` 是一个队列级操作，不是一条命令，它要等一个 binary semaphore 被 signal。

**【发现 12】边界不只是"GPU 到 CPU"这一种，还有层级：命令、submit 批次、队列操作。** present 会强制在它前面切出一个 submit：结束命令缓冲，submit 时 signal render_finished（顺便也 signal timeline N），然后再 present。所以 env 里除了 encoder，还应该能查到"当前 submit 批次"。跨队列（比如 graphics 和 compute）以及 sparse bind 也会切出边界。

**后面的 then（CPU 观察点）**

`then` 的 env 里没有 encoder，所以 present 这一步就是最终边界，等 timeline 的 N。

**【发现 13】timeline 等不到 present 真正完成。** timeline N 只说明渲染命令跑完了，**不代表 present 引擎已经不再用 render_finished 和这张 image**，除非有 `VK_KHR_present_wait` 或 `swapchain_maintenance1` 提供的 present fence。

这带来一个结论：**有些资源的生命周期比 sender 的完成更长。** render_finished 不能放在帧的算子状态里，得挂在 swapchain image 的槽位上，等这张 image 下一次被 acquire 时才能安全复用。这正是上一轮我提到的"按 swapchain image 分配"，现在推演出了原因。

**【发现 14】** present 返回 `OUT_OF_DATE` 或 `SUBOPTIMAL` 时，submit 已经完成了。所以要先等 N，再 `set_error`；如果是 SUBOPTIMAL，则 `set_value` 并带上一个"需要重建"的标记。

**再补一个情形：当前的 recorders 加 when_all**

**【发现 15】** 如果把 `when_all(gpu_a, gpu_b)` 的两个分支放进同一个边界，它们的上游可能在**不同线程**上同时完成，然后并发地往同一个命令缓冲里录，发生数据竞争（命令池需要外部同步）。所以 GPU 域的 `when_all` 必须给每个分支分配**各自的 secondary 命令缓冲和命令池**，合流时在 primary 上调用 `vkCmdExecuteCommands`。你现在的 `recorders` 加 `mutex` 加 `secondary.commands`，手工做的正是这件事。而且合流时要按**分支的声明顺序**执行，不能按完成顺序，否则每一帧的绘制顺序都不固定。你现在的 `push_back` 是按完成顺序排的，这是一个潜在的 bug（菜单只有一个 recorder，所以暂时没有暴露出来）。

**原型实现了什么**

- **D2，完成时间由 env 决定**：同一条链，下游 env 里有 encoder 时，传出的是 `buffer_ref`；没有时，它自己成为边界，传出 `host_view`。`main.cpp` 里用一个 `static_assert` 在编译期验证了这一点。
    
- **合并提交**：`schedule | record(fill) | then | record(copy)` 全部录进同一个命令缓冲，只 submit 一次。中间那个 `then` 在录制时执行，拿到的是句柄。
    
- `**then**` **接在** `**sync_wait**` **前面**：它在 GPU 做完之后才执行，拿到 `host_view`，并且跑在 reactor 线程上（推演【发现 7】）。
    
- **停止和错误都发生在 submit 之前**：提前请求停止时，录完但不提交，直接 `set_stopped`；录制中抛异常时，也不提交，直接把错误传出去。
    

**写代码时新冒出来的细节**

1. **D2 在 stdexec 的类型系统里行得通**，但不带 env 查询签名的那一路，需要调用 stdexec 的内部函数 `__throw_dependent_sender_error`。我没找到公开 API，以后升级 stdexec 时要留意这里。
    
2. **边界必须知道自己属于哪个 context。** 我是通过 sender 属性上的 `get_context` 查询拿到的，所以录制链目前只能从 `schedule(gpu)` 开始。`just(x) | continues_on(gpu)` 这种从 CPU 起头的链还没接上。
    
3. **vkfu 的 stage/access 掩码是位域结构体**，写字面量很方便，但遇到运行时才算出来的掩码只能 `bit_cast`。如果要做自动 barrier，建议 vkfu 提供一个从原始 flags 构造的入口。
    
4. **状态放在值里会出现线性问题**，推演时就预料到了，这次写代码确认了：`copy` 只能返回 dst，src 的状态被丢掉了。正式版需要在 encoder 里维护一张按资源记录状态的表。
    
5. **vkfu 生成的头文件和最新版 Vulkan-Headers 不兼容**（报 `const void*` 的 pNext 错误），必须锁定在 1.4.328。
    
6. 更正一下：前面我在过程中说 vkfu 的 `signal_semaphore` 有 bug，那是我看错了行范围，它没有问题。
