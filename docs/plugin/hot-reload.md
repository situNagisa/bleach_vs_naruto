# 热重载详解（保留教学解释）⭐

> 这是 arT4a 讨论中专门讲透的一块，特此完整保留。

### 0. 「加载插件」≠「热重载」（最常见的混淆）
- **加载插件 (load)**：对局启动时把所有英雄 DLL（你的 + 第三方 mod）载入——**modding 要的是这个**，开局做一次，简单。
- **热重载 (hot-reload)**：对局**正运行时**把某 DLL 换成新编译版本、不重启——**纯粹给开发者加速迭代**，与玩家 / mod 无关。
- 结论：**不做热重载，第三方 mod 系统照样成立**（开局加载即可）。热重载只回答："改了英雄 C++，要不要重启整个游戏才能看到效果？"

### 1. "状态"与"不丢状态"
"状态" = 正在跑的这局的活数据：每个实体的组件（血量、位置、冷却、剑八的连段计数 `jcombo`、蓄力计时 `kHitWindow`、buff…）。
- **不丢状态**：换代码后这局**还在原地**，只有行为按新代码生效，接着测。
- **丢状态 / 不做热重载**：得重启这局，重新摆出测试场景。
- 迭代速度差距：**一小时 5 次 vs 50 次**——这是值得做基建的理由。

### 2. C++ 的死穴：vtable 悬垂
带虚函数的 C++ 对象内部藏着指向**虚表**的指针，虚表住在**旧 DLL 代码段**。卸载旧 DLL → 内存解映射 → vtable 指针变野指针 → 下次虚调用崩。
**状态住哪，决定热重载难度：**

| 状态住哪 | 换 DLL 时 | 结论 |
|---|---|---|
| DLL 里（插件 new 的富对象） | vtable + 内存属旧 DLL，卸载即野 | 丢状态 / 复杂迁移 |
| 引擎里（POD / ECS 组件，DLL 只给函数） | 状态在引擎内存，没被换 | 天然不丢（布局没变） |

> "虚接口 + 富对象 + 直接 ECS"是自由度最高、但对热重载最不友好的一端——所以用工具（路 3）而非架构妥协来解决。

### 3. 几条路（按野心）
- **路 0**：不做 C++ 热重载，只热重载数据 / Lua + 配"秒速测试脚手架"。最省，C++ 改动重启。
- **路 1**：引擎持有 POD 状态 + DLL 热替换（Handmade Hero 式）。状态自动不丢，但英雄写成"函数 over POD"，**牺牲富对象自由度**。
- **路 2**：富对象 + 手写 serialize/迁移。自由度高但每英雄要写迁移、易踩坑。
- **路 3 ⭐**：实时打补丁工具（**Live++** / **blink**）。机器码层面热补丁改动函数，对象 / vtable / 状态全自动保留、即时生效——**同时拿到富对象（最大自由）+ 状态不丢的瞬时热重载**，不写迁移。
  - Live++（商业，有独立定价，业界主流，只增量编译改动 TU——对 C++26 + stdexec 重模板代码是大利好）；blink（开源免费，较老，先试水）。
  - ⚠️ 工具对 **MSVC 最成熟**，clang-cl 需确认；开发 / 热重载构建用 MSVC、发布用 clang-cl 是干净解法。

### 4. 结论
最大自由 + 早投入热重载 → **路 3（blink → Live++）是天作之合**。落地节奏：
- **M0–M2**：路 0 数据 / Lua 热重载 + 开发脚手架；C++ 改动暂重启。
- **M3 起**：接 blink 试水 → 升 Live++，拿到富对象 + 状态保留的瞬时 C++ 热重载。
- 不走路 1 / 路 2 的妥协。
