# bvn 文档规范（doc-spec）

> 本文规定 docs/ 怎么组织、怎么写。分三节：[§1 人和 agent 都读](#1-人和-agent-都读结构与约定)，[§2 给人读](#2-给人读可读性)，[§3 给 agent 读](#3-给-agent-读写作约束防-agent-文档毛病)。
> 文档索引见 [context.md](context.md#bvn-文档索引context)。

## §1 人和 agent 都读：结构与约定

### 1.1 组织原则：模块分离度优先

文档首要目标是**人和 agent 都好读**，而**模块分离度是第一考量**——读一个 theme 时不该被迫牵扯无关文档（对 agent 尤其：避免浪费上下文）。据此：

- **一切按 theme 组织**。`docs/{context.md | doc-spec.md | 全局.md | theme}`。
- **theme 可以是一个 `.md`，也可以是一个文件夹**，按讨论详略而定：
  - 讨论浅的（如 net、asset、platform）→ 单 `.md`，高信息密度讲清思路即可。
  - 讨论详的（如 render）→ 文件夹，下面按子 theme 拆（renderable / renderer / render-scheduler…）。
- **theme 可嵌套**：theme 下可以有子 theme（如 `render/render-scheduler/`）。

### 1.2 四类内容分开：设计 / 规范 / 现状实现 / 计划

**不要把 最终目标、设计思路、当前实现、计划 混在一个文件里**——混在一起难改、交叉引用爆炸、agent 难读。对讨论较详的 theme，按内容分开：

| 类别               | 是什么              | 落点约定                                       |
| ---------------- | ---------------- | ------------------------------------------ |
| **设计（design）**   | 最终想成为的样子、思路、取舍动机 | `*.md` 正文 / `design.md`                    |
| **规范（spec）**     | 终态契约（接口、职责、约束）   | 与设计同文件或 `spec.md`                          |
| **现状实现（impl）**   | 当前阶段实现、为控复杂度的妥协  | `*-impl.md` / `impl.md`                    |
| **计划（plan）**     | 待定、未来向、固化 / 演进计划 | 归入对应 impl 或 spec 末节                        |
| **决策（decision）** | 访谈取舍、为什么这么定      | 全局 `decisions.md` + theme 就近 `decision.md` |

> 例：render-scheduler 的终态设计在 [render-scheduler.md](render/render-scheduler.md#bvn-渲染render-scheduler设计-规范)；模型 A/B 约束在 [render-scheduler/model-ab.md](render/render-scheduler/model-ab.md#bvn-渲染并发模型-a-b设计)。阶段性实现妥协应单独落在仍有效的 impl 文档中，不写回终态规范。

### 1.3 决策归属

- **全局架构决策**（T1–T9 那套：C++ 标准、ECS、并发、确定性…）→ [decisions.md](decisions.md#bvn-技术架构决策日志)。
- **某 theme 内的局部决策** → 该 theme 就近的 `decision.md`（如 [game-design/decision.md](game-design/decision.md#bvn-游戏设计决策记录decision)）。

### 1.4 命名

- 文件 / 目录：`kebab-case`，`.md`。theme 目录名 = theme 名。
- 常见文件名：`design.md` / `spec.md` / `impl.md` / `decision.md` / `model-ab.md` / `<theme>-vulkan-impl.md`。
- 每个文件**开头一句定位**（这文件讲什么、关联哪些文件），紧接正文。

### 1.5 交叉引用约定

- 同目录文件用**裸名**（`renderer.md §2`）；跨目录用**相对路径**（`../animation.md`、`render/boot.md`）。
- 引用带**章节号**便于跳转。正文散文里提到某文档名（非跳转）可不带路径。
- **权威裁决**集中在 [context.md §权威裁决](context.md#权威裁决冲突时听谁的)，不在每个文件头重复声明。

## §2 给人读：可读性

- **高信息密度**：讨论浅的 theme 宁可短，不要为凑篇幅注水。一句话能讲清就一句话。
- **表格优先**：并列的约定 / 对比 / 速查用表，不用长段落。
- **一句话定位开头**：让人 3 秒知道该不该读下去。
- **状态标注**：文件头标 `设计 / 规范 / 现状 / 暂缓 / 讨论浅` 等，让人知道成熟度。
- **中文正文**，代码 / 术语 / 类型名保留英文。

## §3 给 agent 读：写作约束（防 agent 文档毛病）

> 之所以要专门给 agent 立规矩：agent 写文档时有一批系统性毛病，会悄悄引入不必要的实体、增加复杂度、稀释信息。改文档时**必须自查以下几条**。

### 3.1 不要写"不是 xxx / 不做 xxx"，除非语义真会歧义

按文章思路根本不会联想到的东西，**不要因为"会话里讨论过"就写进去否定它**。"我们不用 A、不用 B、不搞 C" 这类否定句会凭空引入 A/B/C 三个实体，读者本来根本不会想到它们。

- **唯一例外**：某处语义**确实容易产生歧义**、读者真会误解时，才写否定——且必须**详细说明为什么这里会误解**。
- 自查：删掉这句否定，读者会不会更糊涂？不会 → 删。

### 3.2 不留已删实体（"不再是 xxx，现在用 xxx"）

已经删掉 / 改名的东西**不要还在文档里被提及**（哪怕是"过去叫 X 现在叫 Y"）。留着它 = 让读者背一个已经不存在的实体。

- 改名 / 重构后，全局搜旧名，**清干净**，而不是加一句"原 X"。
- 自查：这个名字对应的东西现在还存在吗？不存在 → 删所有提及。

### 3.3 不为章节完整性凑空话

不要为了"大纲看起来完整 / 对称"而给一个只讨论了一点点的地方硬撑出一个像模像样的小节。**大纲工整但小节不讲人话、字多信息密度低**，是净损失。

- 讨论浅就短，甚至并进别的节。**没内容的节不建。**
- 自查：这节删掉三分之二字，信息有损失吗？没有 → 就该只留那三分之一。

### 3.4 其它自查

- **不复制正文到索引**：[context.md](context.md#bvn-文档索引context) / 各文件头只放指针和一句话，不搬正文。
- **不重复声明**：同一事实只在一处权威落点写全，别处引用它，不到处复述（否则改一处漏一处）。
- **拆分优先于堆叠**：当一个文件同时长出"设计 + 现状 + 计划"，按 [§1.2](#12-四类内容分开设计-规范-现状实现-计划) 拆文件，而不是在一个文件里堆更多小节。
- **交叉引用要能解析**：写 `见 X.md §N` 前确认 `X.md` 存在、`§N` 存在（改动路径 / 章节后回头修引用）。
